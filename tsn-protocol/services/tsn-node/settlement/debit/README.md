# TIN-Debit components

**Status: implementation under offline verification, November 24, 2026.** This package owns private sender-authorized TIN debit and offline recipient credit. The canonical [contract](../../../../contracts/tin-debit-v1.json) fixes the program/public statement; existing deposit-credit behavior remains separate.

`prepare_tin_debit_request` authenticates short-lived owner consent before returning route/context commitments. `post_tin_debit` validates sender approval and opening consent before encrypted Receiver ingress. The Receiver stores the exact request under its payment ID; retries preserve it. Neither endpoint requests recipient consent. Private inputs are processed by Node and Receiver, while public funding/chain metadata remains observable.

`read_context` and `resolve_debit_asset` authenticate mint/registry/config/reserve/root/verifier layouts, addresses, owners, versions, active approved asset and solvency. Debit eligibility does not depend on `deposits_enabled`. Mutable root and program context come from one confirmed multi-account response. `prepare_work` selects matching snapshots, validates the signed sender head/opening, constructs both encrypted records, proves locally, rechecks context and publishes an immutable root-named candidate. A candidate becomes selected only when the chain root matches it.

`preparation/` contains one function per file for field encoding, commitments, approval/opening verification, authenticated tree arithmetic and record construction. Circuit-owned offline facades import these same functions. Recipient credit uses its authenticated point; no recipient numeric opening is accepted. Unrelated root advances can rebase only with unchanged sender sequence/Memo and valid approval interval. Missing/corrupt snapshots, stale heads, spent nullifiers, invalid signatures and insolvent context fail closed.

`prove` serializes local jobs, applies a timeout and sanitized output boundary, and checks 26 inputs, circuit/key hashes and the 2,284-byte enabled verifier. `public_transition` rejects unexpected fields. `wire` reconstructs the exact 1,128-byte TSNP instruction and two 582-byte Mother Memos. `authorize` rechecks stored attestation, proof, roots, interval and current lease. `verify_message` enforces canonical account set, permissions, config, instructions and Memo pair before the existing Mother-signing boundary.

Inputs and dependencies are explicit function parameters and narrow Protocols; `core/runtime.py` composes the HTTP handlers. Components never import the server or discover mutable application globals. Tests in `tests/test_tin_debit.py` cover unsigned Cranker-to-Node byte agreement and owner preparation/asset predicates; the circuit offline fixtures cover approvals, openings and atomic arithmetic. Exact results and remaining artifact/live checks belong in [verification](../../docs/verification.md).

The separate `GPRU_TIN_DEBIT_*` artifact variables are mandatory for proving. Existing credit/epoch variables and verifier accounts are unchanged. Configuration, deployment, key enrollment and service reload remain operator actions; source tests do not establish those actions or chain acceptance.
