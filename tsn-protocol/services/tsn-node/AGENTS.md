# TSN Node engineering instructions

These instructions apply to this Node directory and its descendants. Read the repository's `AGENTS.md` first, then [the architecture](docs/architecture.md), [the original assessment](docs/original-assessment.md), [the verification record](docs/verification.md), the affected package README, [the complete component inventory](core/component_inventory.json) and [the active-server component map](core/component_contracts.json). This directory is the pilot for the modular engineering standard; changes here do not authorize applying it to another service, SDK, program or repository.

## Component organization

Every authored Python function has its own source file, including class methods, test cases, fixtures, extracted callbacks and small parsing or conversion helpers. Do not hide additional implementations in nested functions or lambdas. Files containing constants, models, Protocol declarations, class shells and explicit exports may contain no function implementation. Class shells attach imported functions with the appropriate instance, class or static method descriptor. Test discovery modules retain explicit exports and class shells; keep individual test implementations under their functional family in `tests/cases/` and new coverage focused on the changed component contract.

Place a component in the existing functional package that owns its responsibility. Use idiomatic Python module names, one clear responsibility per component and explicit named imports. Reuse a compatible component rather than copying its implementation. Keep version-specific implementations only when an actual incompatible contract requires them; do not add speculative version dispatch, fallback implementations or unused subsystems.

The implementation file and package documentation must identify the component's inputs, outputs, dependencies, expected behavior, errors and existing verification coverage. Treat documented entry modules and the original public facades as interfaces. Update their exports and documentation when ownership or a contract changes; do not force consumers to discover a replacement through an unrelated utility module.

## Dependencies and state

`core/runtime.py` is the active application's composition root and owns its mutable Node state. Components requiring that state accept a narrow `Dependencies` Protocol rather than importing `server`, locating the application implicitly or collecting a hidden module-global namespace. Keep callable and configuration dependencies explicit, and use focused type/constants modules and limited local imports to avoid class initialization cycles. Do not use wildcard imports, dynamic code execution or namespace rebinding to simulate modularity.

`core/configuration.py` preserves the active application's configuration. The supporting `app.config` interface has a distinct, older configuration contract; do not merge its defaults or incomplete Solana/epoch helpers into the active runtime. Preserve inherited-process, `.env.local`, then `.env` precedence, the service-root meaning of environment/artifact paths and the working-directory meaning of relative store paths. Never edit credential-bearing environment files merely to make an import or test pass.

`server.py` owns the public HTTP facade, route/middleware registration and existing helper exports. `main.py` retains its alternate entrypoint. Keep these import and startup contracts stable without retaining a parallel runtime implementation. A test that replaces an active dependency should patch the existing runtime member or call the component with explicit local ports; copied facade constants and imported function aliases are not mutable dependency registries.

## Behavior, verification and authorization

This standard permits structural refactoring, not protocol redesign. Before editing, trace the current caller and affected program/account or service contract, preserve every distinct supported capability and record existing failures. Review [the architecture-change policy](https://github.com/bigdreamsweb3/trustlink-pay/blob/main/.agents/architecture-change-policy.md) and the canonical [credit ABI](https://github.com/bigdreamsweb3/trustlink-pay/blob/main/docs/laboratory/credit-abi.md) when changing protocol-facing behavior. Executable layouts and callers remain the source of truth.

Verify meaningful extractions with source compilation, public-interface imports, focused existing tests, dependency integrity and the relevant serialization, authorization or state invariants. At completion, run the complete available offline suite and compare it with the retained baseline, including skips and pre-existing failures. Compare HTTP/OpenAPI contracts separately from transaction bytes. If a check depends on absent tools, native libraries or matching prover artifacts, record that exact limit rather than changing the contract to make the check pass.

Preserve unrelated work, program IDs, keys, deployment configuration and user-managed processes. Do not start/stop services, sign or submit transactions, deploy programs, or commit/push without explicit user authorization. Offline import and test success does not establish startup, a deployed verifier, chain acceptance, owner recovery or transaction completion; report each unperformed check separately.

For changes affecting operation, explicitly read [the operator-guide policy](https://github.com/bigdreamsweb3/trustlink-pay/blob/main/.agents/tsn-operator-guide-policy.md) and [the internal operator guide](https://github.com/bigdreamsweb3/trustlink-pay/blob/main/docs/RUN-YOUR-OWN-TSN.md). For documentation, follow [documentation maintenance](https://github.com/bigdreamsweb3/trustlink-pay/blob/main/docs/DOCUMENTATION_MAINTENANCE.md), review both documentation trees and update only the affected scope. Keep internal installation guidance out of public protocol documentation until publication is authorized, and use repository HTTPS links for any linked file outside the protocol subtree.

Keep documentation modular and synchronized with actual code. Use clear professional explanations, distinct factual paragraphs and useful subheadings; remove rhetorical hooks, dramatic one-line paragraphs, repeated claims and unsupported hype. Report CURRENT implementation, scoped verification, EXPERIMENTAL capabilities and UNVERIFIED results distinctly. Finish a change with the exact validation performed and any remaining gaps.
