# How a TIN credit moves through TSN

A sender identifies a recipient by TIN and approves payment details. The sender's device does not resolve the recipient's TIP route or create the recipient's confidential state. Receiver accepts the signed ingress, and Node resolves TIP and constructs the transaction-specific GPRU transition before the work is released to a Cranker.

```mermaid
sequenceDiagram
    participant S as Sender SDK and wallet
    participant R as Receiver
    participant N as TSN Node
    participant C as Cranker
    participant P as TSN Program
    participant G as GPRU
    participant T as TCAP
    participant O as Recipient SDK

    S->>R: Signed payment details and reserve-funding transaction
    R-->>S: Ingress accepted
    R->>N: Stored work for verification
    N->>N: Resolve TIN through TIP; validate route and asset
    N->>N: Derive unique DNA and one-time ElGamal public key
    N->>C: Release immutable authorized work
    C->>P: Submit authorized credit transaction
    P->>G: Verify DNA-key proof and encrypted-credit relation
    P->>T: Advance shared TCAP commitment root
    T->>T: Check global root predecessor, sequence, asset, and authorization
    O->>O: Discover DNA and derive matching private key locally
```

## What each status means

Receiver acceptance means the signed request passed its ingress contract and was stored. Node verification means the Node independently validated the request and prepared authorized settlement work. Cranker submission means a transaction was sent to Solana. Only chain confirmation establishes that the transaction executed; a later owner state read establishes that the recipient can recover the resulting state.

## What the design protects

TIP stores a stable public scan key for the owner route. GPRU uses it to derive a unique one-time public key for each transaction DNA. The owner can later recover the corresponding private key using owner-held secret material. This is intended to avoid repeatedly exposing one stable recipient address in confidential transaction outputs.

For a debit, GPRU must prove that the encrypted prior balance covers the amount and that the successor is the correct subtraction. For a TIN-to-TIN transfer, it must prove that source debit equals destination credit while keeping the amount private and the DNA outputs distinct. TCAP applies reserve-liability changes only after those checks pass atomically.

Public wallet deposits and exits remain visible at their wallet boundaries. The ElGamal key derivation alone does not prove balance correctness.

## Current status

The current TSN credit ABI passes a hidden-head Groth16 proof to TCAP, which invokes GPRU before atomically advancing one shared global commitment root and reserve liabilities. It does not create a per-TIN TCAP account. Node currently fails closed because the circuit, setup artifacts, witness provider, and prover are not configured. Confidential debit and exit are not established as available end to end.
