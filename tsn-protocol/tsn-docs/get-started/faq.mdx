## What is TSN?

The Transfer Settlement Network coordinates payment authorization and settlement work across TIP identity resolution, Receiver ingress, Node verification, Cranker submission, and Solana programs.

## Is TIP the same as TIN?

No. TIP is the Transfer Identity Protocol. A TIN is one 10-digit Transfer Identity Number managed within TIP.

## What does the current GPRU credit verifier do?

The current TSN credit ABI carries a hidden-head Groth16 proof through TCAP to GPRU. The circuit source represents route membership, latest-head advancement, a nullifier update, and balance transitions. Node currently fails closed because no prover/witness service or generated setup keys are configured.

## Does the current credit path store a TCAP TIP PDA?

The current proof-shaped TSN credit instruction calls TCAP `credit_gpru_memo_v1`, which verifies the GPRU proof before advancing one global TCAP commitment root and reserve liabilities. It does not initialize or update `TCapTinTipV1`. TCAP still contains older TIN-tip instructions in source; they are not part of this proof path.

## What is the hidden-head proof?

GPRU's Groth16 verifier checks a proof that a private TIN head is current, updates its nested token commitment map, binds the Memo, and inserts a nullifier. The updated circuit has nine public inputs and includes Pedersen balance-transition constraints. It has not been recompiled or reviewed; matching keys, a prover, a witness source, an initialized verifier, and end-to-end execution evidence are not established. See [GPRU Groth16 prover setup](/developers/groth16-hidden-head).

## Is the hidden-head design unlinkable?

No. Each transition through that design writes the same public TCAP shared-root account, exposing a common protocol-level link and ordering. The current instruction ABI also exposes action kind, token ID, and amount. The proof aims to conceal which TIN head changed; it does not provide zero linkability.

## Can a user debit or exit confidentially today?

The current source does not establish debit or exit as operational. Those actions need reviewed proof constraints, authorization, reserve/payout checks, a configured prover, and end-to-end on-chain verification.

## How do I know a payment settled?

Receiver acceptance, Node verification, Cranker submission, funding confirmation, and TCAP transition confirmation are distinct. Check the settlement transaction signature and resulting account state on the intended cluster.

## Is the system audited or ready for mainnet?

This documentation does not claim a completed formal audit or mainnet readiness. Verify the current program deployment and security review status before using real funds.

## What about ZK-PRU?

ZK-PRU is historical experiment material, not the current GPRU/TCAP runtime architecture.
