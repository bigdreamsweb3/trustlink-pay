# TCAP reserve and confidential state

TCAP (Transfer Confidential Asset Protocol) governs approved assets, reserve vaults, and protocol liability accounting. For a TIN credit, TSN authorizes a GPRU-scoped transition and TCAP applies the recipient's commitment update through one atomic instruction.

## Credit state transition

The current TCAP credit instruction uses an existing TIP-rooted state account. It checks the authorized asset and policy, the validity window, the expected predecessor commitment, and the next sequence. On success, the instruction advances the successor commitment and sequence and records the transition nullifier in that same account update.

The Node derives the transition nullifier from the exact signed reserve-funding transaction. TSN includes it in the authorization digest and forwards it to TCAP. This binds settlement authorization to funding. TCAP's predecessor and sequence checks make the same settlement transition inapplicable after the first successful state advance, without a separate spent-funding record or per-transaction PDA.

The nullifier field is the current ABI name for this transition value. It is not a nullifier PDA. The stable TIP-rooted state account holds the evolving commitment and sequence needed to validate the next transition.

## Settlement roles

The sender authorizes payment details and signs reserve funding. The Receiver accepts the ingress payload and stores work. The Node verifies the signed authorization and funding, resolves the recipient's TIP route, and constructs the immutable TCAP transition. The Cranker submits the exact Node-authorized transaction; TCAP performs the final atomic state checks.

Receiver acceptance, Node verification, Cranker submission, and TCAP confirmation are distinct lifecycle stages. A funding transaction can confirm while a later settlement remains pending or fails.

## Confidentiality boundary

Credit state is represented by opaque commitments, sequence values, and a funding-derived transition value. These checks do not prove that an encrypted balance is sufficient for a debit. Confidential debit and exit require an audited proof verifier and remain unavailable wherever the on-chain program returns `ProofSystemNotEnabled`.

Wallet funding and exit also expose the public wallet and token-transfer metadata required by those transactions. GPRU's one-time DNA key derivation reduces stable recipient-key reuse, but it does not conceal public funding metadata or independently prove balance correctness.

## Replay and retries

TCAP rejects a stale transition when its predecessor commitment or sequence no longer matches current state. If the state has advanced, a replacement authorization must be constructed from the current state and verified funding outcome. See [Replay Protection and Safe Retry Patterns](/developers/replay-and-retries) for retry behavior.
