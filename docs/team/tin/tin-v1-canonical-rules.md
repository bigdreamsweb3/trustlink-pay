# Canonical TIN V1 Rules
This is the current TIN V1 contract. The Rust program, generated instruction layouts, SDK serializers, Node verifier, Receiver allowlists, and Cranker execution code define behavior. Retired program-assigned and ZK-PRU flows are not compatibility paths.
## Issuance and account layout
The trusted XP issuer generates a random ten-digit TIN, derives a keyed lookup commitment and encrypted identity envelope, and checks that the commitment-derived registry PDA is unused. The TIN program does not generate random numbers or assign TINs.
`TINS_LOOKUP_SECRET` is high-entropy secret material shared only by the trusted issuer and TSN Node. The SDK's identity-envelope helper accepts it for trusted-server use; never put it in browser code, Receiver work, Cranker configuration, or a committed file. The Node fails issuance and resolution closed when it is absent or shorter than 16 UTF-8 bytes. There is no zero-secret or old-route-reader fallback.
The owner signs a canonical UTF-8 message binding the readable approval to the exact TIN V1 intent hash. The SDK, Node, and program hash the owner key, lookup commitment, length-prefixed encrypted recovery/identity/master-seed envelopes, metadata hash, route version and nonce, TCAP route version/commitments, and expiry in the same order. Node additionally checks the issuer HMAC proof, expiry, owner signature, and replay-protected owner/nonce pair before Receiver marks work `VERIFIED`.
`CreateTinV1` consumes the existing global-state PDA, commitment-derived registry PDA, owner-indexed recovery PDA, instructions sysvar, and system program. The global state must be initialized once before issuance; creation increments its sequence. The registry stores the keyed lookup commitment, owner hash, encrypted identity and master-seed envelopes, and current TCAP relationship fields. The separate owner-recovery PDA stores only the wallet-encrypted recovery envelope. No plaintext TIN or display name is stored on-chain.
Large creation payloads use the on-chain staging account. Staging accepts only encrypted identity, encrypted master-seed, and encrypted TIN-recovery chunks (up to 700 bytes each), then finalizes through the same `CreateTinV1` validation. There is no public-route-envelope blob in the current layout.
## Service boundaries
```text
Owner device + trusted issuer -> Receiver ingress -> Node verification
  -> Receiver VERIFIED work -> Cranker lease -> Solana TIN V1 program
```
Receiver owns durable work and leases. It accepts only the private TIN V1 creation allowlist and never gets the lookup secret or plaintext identity. The Node verifies Receiver-leased work and returns a signed decision; it does not issue TINs or submit transactions. Cranker executes only a valid Node-attested Receiver lease. A TIN is final only after the creation transaction is confirmed and the registry account is checked.
## Recovery and resolution
The owner-indexed recovery PDA enables wallet-only discovery of that owner's encrypted recovery envelope. The SDK fetches it by owner PDA and decrypts it locally after a fresh wallet signature; current records use V4 recovery envelopes, while V2/V3 support is read-only compatibility for recovery ciphertexts. The registry itself is not enumerable by owner.
`GET /tin-resolution/{tin}` uses Node-held lookup material to resolve the encrypted identity. This endpoint does not require owner-wallet authentication: anyone who knows the TIN can request its display identity. Do not describe the response as owner-authorized. Do not expose the lookup secret or add a plaintext wallet-to-TIN index.
## Payment routing
A sender authorizes the recipient TIN and signs the supported TCAP deposit funding transaction. Sender authorization and Receiver work do not carry recipient route commitments, PRU balances, PRU selections, or the lookup secret. Node reads the active TIN V1 TCAP relationship from chain and independently validates/builds the TCAP V2 credit transition. Current funding ingress accepts `tcap_deposit_v2`; wallet-only, PRU-only, and mixed-funding variants are retired.
## Deployment and verification
Program deployment alone does not initialize global state. Before issuing, initialize the program's global-state PDA once using the repository's TIN initializer and confirm the real transaction. Do not treat a pending Receiver operation, a Node `VERIFIED` decision, a Cranker lease, or a staging transaction as issuance evidence. Record the final creation signature, registry PDA, and account validation only after Solana confirms finalization.
Never use retired `programAssigned` payloads, owner-derived legacy registry PDAs, `programAssigned: false` flags, public PRU-route envelopes, old TIN upgrade flows, direct Node TIN-operation endpoints, or compatibility fallbacks for new work.
