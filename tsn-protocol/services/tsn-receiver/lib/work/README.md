# Receiver durable work components

The stable `../store.ts` facade binds the original fourteen operations and the added `attachSignedFunding` operation to dependencies composed in `runtime.ts`. Individual components receive only the persistence, verification, payload, notification or entropy operations they use. `dependencies.ts` declares the actual query, document, snapshot and transaction ports; components do not initialize Firebase or import a route to locate state.

Message-only ingress persists `AUTHORIZATION` work and its immutable authorization commitment without creating settlement. A signed `FUNDING_READY` decision encrypts the private preflight and retains its original attestation and Receiver lease context. Atomic signed-deposit attachment requires current readiness, expiry/version/commitment checks, preserves the original authorization, and creates settlement from the completed funding commitment. Exact repeats succeed; replacements fail. Only final Node verification enables a Cranker. Wakes follow durable transactions, and confirmed funding remains mandatory before settlement verification. The named lease components retain reclamation, supported-kind selection, accounting priority, shared-root locking and existing durations; signed checkpoints and receipt reconciliation retain their separate authority.

`snapshot-work-data.ts` serves the three compatible list projections. Existing contract field components serve funding-receipt filtering and checkpoint entries. The [callback map](callback-extraction-map.json) records the replacement for each original callback; reused helpers do not retain an alternate implementation.

`leaseForNode(owner, supportedKinds, fundingPhase?)` accepts `AUTHORIZATION` or `SIGNED_DEPOSIT` only with exactly `["AUTHORIZED_FUNDING"]`. [Filter validation](assert-node-funding-lease-filter.ts) rejects other combinations before storage access. The [phase predicate](matches-funding-lease-phase.ts) restricts selection and expired-lease reclamation, and the claim transaction rechecks persisted phase atomically. Each filtered miss returns `null`. Node uses independent signed-funding and ordinary workers; the latter prepares message-only authorization before coordination and selects nonfunding kinds for its ordinary claim. Generic unfiltered Receiver calls retain accounting priority, randomized peer order, shared-root locks and existing version/expiry checks.

The exact-baseline differential review compared all fourteen public export names/arities and sixty deterministic operation results, durable states and transaction/wake traces. It exercised synthetic in-memory persistence, including rollback, idempotency, lease renewal, checkpoints, terminal replay, expiry and pagination. Existing Receiver suites provide additional characterization; those checks do not establish hosted Firestore parity, live service availability or chain execution.
