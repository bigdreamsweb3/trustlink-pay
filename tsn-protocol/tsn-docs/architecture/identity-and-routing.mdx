# TIP, TIN, and GPRU routing

The **Transfer Identity Protocol (TIP)** manages transfer identities and their route metadata. A **Transfer Identity Number (TIN)** is one 10-digit identity issued within TIP; TIN is not the name of the entire protocol. **GPRU (Guarded Privacy Routing Unit)** creates transaction-specific routing keys and verifies their derivation proof for TSN credit settlement.

## What TIP and TIN provide

A TIN lets an application address a recipient through a transfer identity instead of asking the sender to use a recipient wallet address. Resolving a TIN can return user-approved display information and the route metadata required by an authorized service. A TIN is not a wallet, token account, private key, or balance account.

The TIP V1 registry stores public commitments and encrypted identity/recovery data according to its account layout. The owner-recovery record is a separate PDA owned by the TIN Registrar program. It is derived using the `tin-v1-owner-recovery` seed and owner wallet public key, and stores the owner public key and encrypted recovery envelope. The connected owner wallet allows the SDK to derive that PDA and decrypt the recovery envelope locally. This recovery record is distinct from the main TIN registry record.

## Current GPRU route material

The current TIP V1 route includes a versioned GPRU ElGamal scan public key and a commitment to that key, plus TIP route and policy commitments. The scan public key is stable for the route; the owner retains the matching secret material. Its key commitment is a domain-bound integrity check for the key/version and is not itself a private key, proof of ownership, or balance proof.

## Transaction-specific routing

For each transaction, Node creates a unique DNA and uses fresh randomness with the TIP scan public key to derive an ephemeral point and one-time ElGamal public key. Node can construct that public output while the recipient is offline. Later, the recipient SDK combines the public DNA inputs with owner-held secret material to derive the matching private key locally.

The SDK should submit the sender's authorization and funding details. It should not resolve the recipient TIP route or construct the recipient's GPRU transition. Receiver accepts and stores ingress; Node resolves TIP, validates the request, and constructs immutable settlement work; Cranker submits that work without changing it.

## Privacy and security limits

The on-chain GPRU proof validates one-time-key derivation; it does not prove that a credit or debit has a valid encrypted-balance transition. TSN and TCAP enforce authorization, asset, policy, predecessor, and sequence checks for credit. Confidential debit remains disabled until an audited balance-proof verifier is enabled. The SDK can check an owner's local balance for feedback, but that check cannot authorize a debit.

Public wallet deposits and exits expose transaction data at the wallet boundary. Unique DNA outputs are intended to reduce stable-recipient linkability; they do not make those public transactions anonymous.

## Current implementation status

TIP V1 contains the stable scan public key and commitment. The repository contains the GPRU derivation library, Node native adapter, SDK owner-recovery helper, and on-chain DNA key proof instruction invoked by TSN during TCAP credit settlement. Encrypted-balance proofs and confidential debit/exit are not part of the current flow. Current program source and account layouts remain authoritative for live behavior.
