# Architecture contradictions and claim coverage

**Status: CURRENT reconciliation record, reviewed 2026-11-02.** This register records specific disagreements and their resolution from executable contracts. The [document inventory](../references/documentation-inventory.json) classifies every discovered relevant Markdown/MDX file. The [technical claim inventory](../references/technical-claim-inventory.json) adds paragraph/list/code review units with source positions, stable content hashes, disposition, evidence and explicit claim overrides. Classification is not equivalent to successful execution.

## Resolved disagreements

1. **Prover and witness existence.** Earlier `CURRENT-ARCHITECTURE.md` said there was no witness source, generated key artifacts or locally tested prover. The current Node has `hidden_head_witness.py`, `hidden_head_prover.py` and a source-bound Node proving script. Dated development setup/key verification and local tests are recorded in [EXP-20261102](experiments/EXP-20261102-hidden-head.md). The corrected claim distinguishes implemented local adapters from absent runtime settings and unverified live settlement.
2. **Recipient hash.** The previous public getting-started example assigned the ten-digit TIN to `recipientHash`. The SDK request builder and Node verification require the resolved 64-character hexadecimal `ownerPubkeyHash`. [The payment guide](../../tsn-protocol/tsn-docs/sdk/payment-guide.mdx) and complete typed examples now use the actual contract; the canonical route tests reject sender-supplied route data.
3. **Instruction order.** A public confidential-settlement diagram placed GPRU before TCAP. The native call is TSNP authorization → TCAP checks/CPI → GPRU verification → TCAP root/liability update. [The explicit ABI guide](credit-abi.md) records account order and proof fields. GPRU is a verifier invoked by TCAP, not an independent custodian or settlement submitter.
4. **Funding versus settlement work.** Receiver creates linked settlement work during funding ingress. The settlement cannot be leased for Node verification until its funding is confirmed. Corrected [lifecycle](architecture-map.md) documentation preserves both facts; it does not describe settlement creation as proof of a funded or authorized transition.
5. **Cryptographic input count.** A lingering diagram used nine public inputs. Current circuit/serializer/verifier contracts use twelve public inputs and thirteen IC points. [Cryptography](cryptography.md) and [credit ABI](credit-abi.md) link the ordered relation; a key for another R1CS cannot be reused because a file name still contains V1.
6. **TIN creation fields.** Retired TCAP relationship/private-routing payload names conflicted with current TIP/GPRU commitments, owner recovery, ElGamal key and BabyJubjub scan-key fields. [Canonical issuance stages](../protocol-flows/tin-creation/README.md) preserve direct/staged creation with current ingress fields. The old handoff/dataflow narratives are explicitly retired and indexed rather than deleted.
7. **Epoch/reimbursement versus native credit.** Existing epoch treasury, AcceptedIntent, Settlement DNA, payout and refund code remains a separate instruction family. It is not a prerequisite stage of wallet reserve deposit followed by hidden-head credit. [Component records](components.md) describe its accounts and boundaries without assuming that every retained entrypoint is live.
8. **Privacy guarantees.** Several pages asserted that timing/shared roots do not establish recipient correlation or implied owner-only lineage knowledge. Current proof hides the TIN/predecessor witness but publishes amount, asset, shared roots, nullifier, successor point and ciphertext. Node handles private resolution/witnesses. [Public threat boundaries](../../tsn-protocol/tsn-docs/security/threat-model.mdx) state the encoding and operator assumptions; no general unlinkability or confidential exit guarantee follows.
9. **Readiness versus availability.** SDK `readyForNativeTransactions` is based on reachability probes. It does not check verifier installation, root snapshots or recipient schema. Examples/guides now separate health from account/proof readiness and successful settlement.
10. **Research publication versus present contract.** The independent research checkout still uses ZK-PRU and an earlier TCAP expansion. Published status does not establish compatibility with current instructions. [The historical archive](../historical-archive/README.md) preserves papers unchanged and records the naming/architecture mismatch.
11. **Declared repository layout versus actual Git boundaries.** `.gitmodules` and package metadata imply repositories not present as independent checkouts. The [architecture map](architecture-map.md) records the actual boundaries. The docs pull script refuses this existing non-standalone documentation directory; using it would not be a safe refresh method.

12. **Public deposit-nullifier linkage.** Current Node derives the published credit nullifier from public TCAP program/deposit-signature bytes and a fixed domain. An observer can recompute the funding-to-credit link. This contradicts earlier no-public-funding-pointer claims, while the recipient TIN witness remains hidden. [The exact construction](cryptography.md) distinguishes replay binding from unlinkability and records the unresolved privacy-design tradeoff.

13. **Registry versus global-state version.** Earlier current guides called fresh TIN registration schema 3. TIP `state.rs` uses `CURRENT_VERSION=3` for global state and `TinV1Account::VERSION=1` for the current registry; staging is version 4. The [successful run](experiments/EXP-20261102-tin-staged-finalization.md) independently found registry version 1. Current guides now use the actual registry/layout contract. Older readiness descriptions retain their original schema labels with an explicit correction, and an account version byte alone does not prove old-layout compatibility.
14. **Cranker fee payer and confirmation scope.** The public operator guide implied Cranker pays every submitted Solana fee. Current funding wire fixes the SDK depositor as payer; Cranker pays its constructed TIN/native-credit transactions. The [transaction map](cranker-transaction-map.md) also distinguishes terminal daemon reports from Receiver's available SUBMITTED state, and Creditcoin hub confirmation from destination payout.

## Execution handoff correction

**Node/Receiver native authorization envelope.** The earlier `{transition, workStateVersion}` response omitted Receiver's lease fields and Cranker's kind. The corrected handler returns `TSN_TCAP_GPRU_CREDIT_AUTHORIZATION_V2`, the exact verified transition, current lease ID/version/expiry and lease-bounded `expiresAtTs`. Local tests exercise envelope fields, expired/unrelated leases and lease rotation. [The map and source links](cranker-transaction-map.md#nodereceiver-lease-authorization) distinguish this correction from the still unverified live settlement and DBrix V1 cluster acceptance.

**TCAP credit asset offsets.** Node's preflight treated bytes 245–248 as a credit availability tuple and falsely rejected an Active/Approved asset with withdrawals disabled. The program stores status/risk/deprecation at 283–285 and separately checks pause at 247 and reserve binding. The corrected preflight matches `CreditGpruMemoV1`; [the transaction-map checkpoint](cranker-transaction-map.md#corrected-tcap-asset-preflight-2026-11-02) records regression coverage and read-only reserve validation. The authenticated retry admits this exact preflight rejection for fresh verification, preserving the already confirmed deposit.

## Remaining claim review

Whole-page CURRENT means a reviewed source narrative, not a tested deployment. VERIFIED labels apply to specified observations with linked evidence; environment observations retain their captured date/slot. Legacy runbooks, research assertions, generalized cross-chain execution, threshold-provider activation, historical selection rationale and many generated JSDoc assertions remain UNVERIFIED where the supporting evidence is insufficient. Generated TypeScript signatures describe source contracts but do not make every associated comment true.

The claim inventory deliberately includes code/diagram units without copying their bodies; complete examples, source extraction and syntax reports supply different evidence. A prose paragraph can contain several assertions, so a future detailed review should split a mixed paragraph into individually scoped claims and record evidence per claim. The register does not claim that an automated paragraph extraction proved every sentence. Re-run inventory after edits so positions/hashes remain useful.

## Maintenance procedure

Record an exact claim selector and supporting source/test in [claim-review.json](../references/claim-review.json). The generator fails when a selector stops matching, preventing silently stale evidence attachments. When source changes, review dependent architecture/lifecycle/ABI pages before regenerating signatures. Keep archived hypotheses, actual experiments and reconstructed ADR decisions distinct, and preserve original unknown dates/alternatives as unknown.

Use [DOCUMENTATION_STATUS](../DOCUMENTATION_STATUS.md) for the completed scope, exact checks and ordered continuation work. It identifies coverage limits without promoting missing history or live verification into established behavior.
