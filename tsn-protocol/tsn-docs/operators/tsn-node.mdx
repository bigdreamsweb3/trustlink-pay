The TSN Node is a service role in the wider TSN infrastructure. It verifies payment work against the sender's authorization, applicable identity route, and funding evidence, then prepares eligible work for on-chain execution.

The Node does not itself settle a payment. A Cranker submits authorized work, and Solana program checks determine whether the requested state change can execute. Node verification and chain confirmation are separate events.

GPRU guards the integrity and privacy of user state presented to TCAP. TCAP remains responsible for accepted assets, reserves, and atomic settlement. The hidden-head proof path is not yet established end to end.

This site explains protocol roles and application SDK use. Node deployment, configuration, and operational procedures are maintained in the [repository documentation](https://github.com/bigdreamsweb3/trustlink-pay/tree/main/docs).

## Integration and operating prerequisites

The inspected Node uses authenticated Receiver work leases and signs an allowlisted execution projection. Its verification credential, Receiver worker credential and Mother chain authority have distinct roles. Native credit also requires pinned circuit/WASM/key/metadata artifacts, root-matching witness snapshots, a matching initialized GPRU verifier, active TCAP state and a valid recipient route. A Node HTTP health response does not prove these conditions.

The private-credit source requires an initialized global TCAP funding root and a thirteen-input V2 verifier with the matching private-amount circuit key. Node checks the private opening against the commitment signed in both payment approval and deposit, reconstructs public funded membership, and proves the exact asset/amount with a deterministic secret-derived nullifier. Receiver stores the opening only in the encrypted Node envelope; public decisions, Cranker payloads and authorization responses exclude it. Protect the decrypted opening in the verification environment and omit it from logs.

Funding snapshots contain only public leaves and extend a validated prefix to the chain-selected root/count. Recovery requires successful TCAP append receipts and is bounded to 10,000 leaves/signatures. Credit selects a released immutable sealed funding pool, so later deposits preserve that membership root. Unsealed pool work must be verified again if the global funding root changes before capture. Old signature-only pending deposits have no new-tree membership and cannot use a runtime fallback. Use the native Poseidon adapter with arities one through five and apply matching circuit/key settings under operator control. Existing settled TCAP state and historical owner receipt decoding remain separate preserved capabilities.

Protect lookup material, decrypted ingress and private witness data in the verification environment. Persist coordination through the configured Receiver state APIs, keep chain/RPC configuration consistent, and retain sanitized decision reasons and confirmed signatures for diagnostics. The source does not establish a permissionless multi-Node consensus or high-availability deployment guarantee.

TIP creation advances its append-only route root. Before settlement proving, Node automatically validates the matching local TIP snapshot or reconstructs the missing routes from confirmed creation history. It uses TIP's append indices, supports direct and staged creation, validates public registry bindings, and requires the ordered leaves to match the chain root and count before publishing. Earlier snapshots are preserved; owner envelopes are not decrypted. A cold Node can rebuild from creation index zero when the RPC retains the required history.

Configure `GPRU_HIDDEN_HEAD_WITNESS_DIR` as the Node's persistent witness directory and keep access to confirmed creation receipts. Automatic synchronization is bounded to 10,000 routes and 10,000 scanned signatures; missing history, invalid accounts or a changing root remain explicit failures. `scripts/sync-tip-witness.py` remains an operator diagnostic using the same validation/publication code. TCAP state snapshots use their separate existing candidate mechanism; TIP synchronization does not reconstruct a missing TCAP state snapshot or retry rejected work.

The corrected settlement authorization response includes `kind=TSN_TCAP_GPRU_CREDIT_AUTHORIZATION_V3`, the exact stored transition, current lease ID/version/expiry and `expiresAtTs` bounded to that lease. Changed, unrelated or expired leases fail. Local tests cover the response contract; they do not establish live chain credit. After a missing-snapshot or the exact repaired TCAP asset-preflight rejection, use Receiver's guarded retry for the already funded settlement after loading corrected services, preserving independent Node verification and confirmed funding.

Node's credit preflight follows the deployed account layout: asset status/risk/deprecation appear after governance approval, separately from deposit/withdrawal/policy flags. Credit requires an Active/Approved, unpaused, nondeprecated asset bound to the reserve; disabled withdrawals do not prohibit credit. Requeueing after the offset correction still requires current account, reserve, root, slot and proof validation.

Verification can exceed the initial 60-second Receiver lease while constructing a witness and proving. Node now confirms and renews that active claim every 15 seconds through the authenticated work PUT operation, preserving the version used by its decision attestation. Renewal runs through reporting and stops when work completes; lost ownership cancels verification without publishing a decision from the stale claim. Processing is bounded to 600 seconds, and the prover retains its separate 300-second invocation limit. No renewal or queue polling runs while the worker is idle.

## Pool release and authorization timing

Node selects a common adaptive release boundary after validating the positive unspent pool members and rereading the current funding root. It budgets time for the later lease authorization and Mother co-signing checks. Each authorization rereads root/count/slot after its census; an expired boundary or changed root returns `TCAP_POOL_CAPTURE_STALE` for unsigned work to be verified again. The sanitized Node log records that reason. Slow RPC can extend the selected window; this does not relax the two-wallet minimum or establish a latency guarantee.

## RPC availability and signed funding

The Node simulates the exact owner-signed deposit with signature verification enabled and blockhash replacement disabled. When every attempted endpoint explicitly rejects the hash, the sender needs a freshly signed transaction after checking the original attempt. A mixture of rejection and unavailable/malformed RPC results leaves validity unknown. Temporary HTTP 5xx/transport failures retry during the active renewed claim, bounded by the 600-second processing window; they do not become a terminal invalid-approval decision. Lost ownership cancels reporting. See [failure recovery](/sdk/troubleshooting).
