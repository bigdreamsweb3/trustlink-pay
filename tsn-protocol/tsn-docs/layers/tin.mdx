title: "TIN Layer: Transfer Identity Number and Route Discovery"
sidebarTitle: "TIN"
description: "TIN is the 10-digit Transfer Identity Number issued by the Transfer Identity Protocol. It resolves payment routing without exposing a wallet address."
---

**In plain English:** TIN is a portable, human-readable 10-digit payment identity. A sender shares the TIN and can confirm the resolved recipient name before authorizing a transfer, instead of copying a long wallet address. The TIN routes a payment; it does not hold tokens or replace the owner's wallet authority.

## What TIN is (and is not)

| Wallet address                               | TIN                                                        |
| -------------------------------------------- | ---------------------------------------------------------- |
| Public cryptographic account identifier      | Payment identity and route-discovery identifier            |
| Identifies a public key or account authority | Resolves permitted payment routing metadata                |
| May own token accounts                       | Does not itself hold tokens or act as a private key        |
| Usually exposed directly                     | Binds to the TCAP relationship and encrypted snapshot path |

TIN is not a private key or token account. A confirmed TIN V1 binds to an owner wallet and encrypted identity data. A sender can use the resolved display name as a payment-confidence check; that name alone is not legal verification or payment authorization.

## Registrar program

<Note>**Status: Live on Devnet.**</Note>

The current TIN V1 registry derives its PDA from a keyed lookup commitment,
not from a public TIN or owner wallet. The trusted issuer and Node share a
high-entropy `TINS_LOOKUP_SECRET`; there is no all-zero public fallback. The
secret is required to derive the commitment and decrypt the identity envelope,
and must never enter a browser, Receiver payload, or Cranker request. The
program records the owner authorization and encrypted identity; it does not
generate the random ten-digit number. The trusted issuer generates the TIN,
checks that its commitment PDA is unused, and submits the owner-authorized
creation through Receiver, Node verification, and Cranker execution.

The V1 route binds the GPRU public commitment to its blinded TCAP TIP-seed
reference and policy commitment. Earlier account layouts and PRU route fields
are rejected by current TIN V1 creation and resolution.

Current TIN V1 SDK helpers derive these PDAs:

| Helper | Seeds / derivation |
| --- | --- |
| `getTinV1CreationStagingPda` | `tin-v1-create-stage`, owner key, intent hash |
| `getTinV1OwnerRecoveryPda` | `tin-v1-owner-recovery`, owner key |
| TIN V1 registry PDA | `tin-v1`, keyed lookup commitment |

## Resolution flow

1. The sender supplies the 10-digit TIN to the application.
2. The application requests display identity from the TSN Node resolution
   endpoint; Node derives the registry PDA with its protected secret, validates
   current TIN V1 state, and decrypts the identity disclosure.
3. The SDK builds the sender authorization using the TIN and resolved display
   identity. The sender does not sign a client-supplied route commitment.
4. At payment ingress, Node independently resolves the current on-chain TIN V1
   TCAP relationship and constructs the recipient transition from that route.

Resolution is by requested TIN, not public registry enumeration. The endpoint
returns identity disclosure, never plaintext seeds or child private keys.

## Record classes

| Class              | Examples                                                          | Boundary                                            |
| ------------------ | ----------------------------------------------------------------- | --------------------------------------------------- |
| Public             | Program ID and commitment-derived account address                 | Does not expose a wallet-to-TIN index               |
| Integrity metadata | Owner authorization, route commitments, state version             | Verifiable protocol data, not the plaintext TIN     |
| Encrypted          | TIN and display name envelope; wallet-protected master-seed data   | Ciphertext stored with the registry                 |
| Off-chain app data | Optional profile or notification references                       | Stored under the app's own access policy            |

## Ownership and recovery

The owner wallet authorizes TIN creation and is stored in the registry record.
A separate PDA indexed by owner stores only the encrypted recovery envelope;
its one-per-owner initialization prevents multiple recovery locators for the
same wallet. When the owner reconnects, the SDK reads that ciphertext and
requires a separate domain-separated wallet signature to decrypt it locally.
The raw recovery signature, TIN, and display name are not sent to Node or
Cranker as part of recovery.

The recovery locator does not reveal the TIN or derive the registry PDA. The
registry is found through its keyed lookup commitment, while the owner PDA only
locates the ciphertext. Registry uniqueness follows from the keyed commitment
PDA; owner uniqueness follows from the recovery PDA. Receiver and Cranker
receive only the recovery ciphertext and other encrypted fields.
