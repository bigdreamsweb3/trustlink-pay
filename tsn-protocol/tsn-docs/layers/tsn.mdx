TSN is the Transfer Settlement Network. Its service layer coordinates signed intents, Receiver work storage, Node verification, Mother authorization, and Cranker transaction submission. Its Solana program enforces the relevant authorization and CPI checks; it does not decrypt user balance data.

## Wallet-to-TIN credit coordination

The sender authorizes payment and reserve funding. Receiver accepts and stores the ingress. Node verifies the request and resolves the TIP route, then releases authorized work. Cranker submits the authorized transaction. In the current credit source, TSN verifies GPRU's DNA-key proof and invokes GPRU credit-transition validation followed by TCAP's shared-root credit transition.

This path advances a single shared TCAP root. It does not use the hidden-head Groth16 instruction currently present in GPRU and TCAP source, and it does not establish a persistent latest ciphertext for each TIN. See [GPRU and TCAP state](/architecture/gpru-confidential-balances).

## Other TSN instructions

The TSN program also contains epoch, Mother authorization, and settlement/refund instruction families. Their presence in source is not evidence that a particular XP transaction uses them. A given route must be traced from its Node/Cranker caller through the exact top-level instruction before describing its runtime behavior.

## Lifecycle evidence

Receiver acceptance, Node verification, Cranker lease/submission, and Solana confirmation are separate milestones. A confirmed funding transaction does not establish that the follow-up TCAP state transition succeeded. Only the transaction signature and resulting on-chain state establish execution on a specific cluster.
