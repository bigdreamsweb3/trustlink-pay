# A private TIN payment

The sender uses a TIN to identify the recipient, reviews the identity details returned for that request, and signs the payment and funding authorization. Node resolves the recipient's TIP route after Receiver accepts the signed request, then constructs the recipient-specific GPRU transition. The sender's device does not receive the recipient's private route state.

Each GPRU output uses a unique transaction DNA and one-time ElGamal public key. The recipient can later recover the corresponding private key locally from owner-held secret material. GPRU must verify the encrypted balance transition before TCAP changes reserve liabilities.

```text
Sender signs payment and funding authorization
  → Receiver accepts and stores ingress
  → Node resolves TIP and validates the request
  → Node constructs unique GPRU DNA work
  → Cranker submits immutable authorized work
  → GPRU verifies proof and replay protection
  → TCAP applies the reserve-liability update atomically
  → Recipient recovers and reads state locally
```

Receiver acceptance is not Node verification. Node verification is not Cranker submission, and submission is not confirmation. Public wallet funding and exits remain visible at the wallet boundary.

The one-time key derivation and SDK recovery helper are in source, but the deployable GPRU program, proof verifier, and TCAP integration remain future work. For a detailed flow and status, see [How a TIN payment works](/overview/how-it-works) and [GPRU and TCAP confidential state](/architecture/gpru-confidential-balances).
