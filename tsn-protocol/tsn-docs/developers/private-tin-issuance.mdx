TSN TIN V1 keeps the TIN and display name out of Receiver work and the on-chain
account. The XP backend generates a random ten-digit TIN, checks that its
keyed registry address is unused, encrypts the identity, and submits only the
owner-authorized V1 payload through Receiver ingress. The TIN is shown to the
owner after the Cranker confirms the Solana transaction.

The TIN V1 program does not generate random numbers. The backend performs
random issuance; the program verifies the signed commitment and creates the
`TinV1Account` at its commitment-derived PDA. Never describe this as the
program assigning a TIN.

## Service boundary

```text
Owner wallet -> TSN XP + SDK -> Receiver queue -> Node verification -> Cranker -> TinV1Account
```

`TINS_LOOKUP_SECRET` is the legacy configuration name for the value used to
derive the lookup commitment and identity-envelope key. The universal issuer
uses the public all-zero value so any integrated app can resolve its TINs;
this intentionally makes universal TIN/name records enumerable and is not a
confidentiality key. An institutional issuer can configure a high-entropy
private value to restrict its own identity lookup. Receiver work carries the
derived commitment and encrypted envelope, not the configuration value. The
Node validates the owner signature, canonical intent hash, and issuance proof
before marking work eligible for Cranker processing.

## Creation sequence

1. The XP backend generates a random TIN and derives its keyed lookup PDA.
2. It checks Devnet for an existing account at that PDA and retries if occupied.
3. The SDK encrypts the TIN and display name, then builds the V1 owner intent.
4. The wallet signs the deterministic UTF-8 owner-approval message. That
   message contains the 32-byte intent hash in hex; the program verifies the
   same message through the Ed25519 instruction immediately before creation.
5. The SDK submits the commitment, ciphertext, proof, and signature to Receiver.
6. The Node verifies the Receiver work; the Cranker serializes and submits
   `CreateTinV1`.
7. The XP backend reveals the generated TIN to the issuing browser session only
   after Receiver reports the Cranker transaction as confirmed and the SDK
   resolves the registry identity. Reconnecting a wallet does not currently
   recover a TIN automatically; the registry is not publicly enumerable by
   wallet.

If the complete transaction fits Solana's 1,232-byte packet limit, the Cranker
submits one creation transaction. Larger payloads use the on-chain staging
account: initialize an intent-bound stage, append encrypted blobs in chunks of
at most 700 bytes, then finalize with the owner proof and `CreateTinV1` checks.
The finalization signature, rather than a staging signature, proves registry
creation. The service-by-service lifecycle is documented in the repository's
canonical TIN V1 flow guide.

The intent hash covers the owner, lookup commitment, length-prefixed encrypted
blobs, metadata and route commitments, route nonce, and expiry. The Rust
program, SDK serializer, and Node verifier use the same field order and
encoding. The separate HMAC issuance proof binds the commitment to the owner,
intent hash, nonce, and expiry without disclosing the TIN.

## SDK primitives

The SDK accepts the namespace lookup value when creating or resolving the
identity envelope. The universal value is public; an issuer-specific private
value must stay on trusted services and out of Receiver payloads. The wallet
remains the user's ownership and authorization anchor. The product requirement
is wallet-only recovery: after connecting, the owner should see the existing
TIN without memorizing or re-entering its digits. The current XP does not
implement this, and its creation path also does not enforce one TIN per wallet
in the universal issuer namespace. Implement an owner-bound recovery record
and an on-chain uniqueness check before calling this flow complete.

```ts
const identity = await createTinV1IdentityEnvelope({
  tin: generatedTin,
  displayName,
  lookupSecret: TINS_LOOKUP_SECRET,
});

const prepared = buildTinV1Creation({
  ownerPubkey,
  lookupCommitment: identity.lookupCommitment,
  encryptedIdentityEnvelope: identity.encryptedIdentityEnvelope,
  encryptedMasterSeed,
  tcapRouteVersion: 1,
  tcapRelationshipCommitment,
  tcapRelationshipReference,
  tcapPolicyCommitment,
});

const ownerSignature = await wallet.signMessage(
  buildTinOwnerIntentMessage(prepared.intentHash),
);
await submitTinV1Creation({
  ingressUrl: TSN_RECEIVER_URL,
  prepared,
  intentId,
  ownerPubkey,
  ownerSignature,
  lookupIssuanceProof,
});
```

The signature covers the SDK's canonical UTF-8 approval message, which binds
the readable approval to the exact intent hash. The Cranker places that same
message and signature in the Ed25519 verification instruction consumed by
`CreateTinV1`; a signature over the raw hash or a different message is not
interchangeable.

## Resolve a TIN and prepare a transfer

The trusted resolver derives the same PDA with the protected lookup secret.
The SDK decrypts the identity envelope only after resolving the V1 account.

```ts
const identity = await resolveTinRoute({
  tin: recipientTin,
  rpcUrl: TSN_RPC_URL,
  programId: TIN_PROGRAM_ID,
  lookupSecret: TINS_LOOKUP_SECRET,
});
```

Use the returned TCap relationship commitments in the SDK payment
authorization. Do not pass the lookup secret into Receiver work or Cranker
payloads.

For wallet-to-wallet SPL transfers, use
`buildTsnSplTokenTransferTransaction` from the SDK and let the connected wallet
sign the returned unsigned transaction. Private TIN routing and ordinary
wallet transfers remain separate flows.
