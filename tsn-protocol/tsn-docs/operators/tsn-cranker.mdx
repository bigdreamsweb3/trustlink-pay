A Cranker is an independent transaction-submission role in TSN. It receives work that has already passed the required service checks, submits the authorized transaction to Solana, and reports the resulting signature and status.

A Cranker cannot change the sender's authorized amount, recipient, asset, or settlement conditions. Its submission is not proof of success; the transaction must confirm on chain. The Cranker does not replace GPRU's private-state guard or TCAP's authority over assets and settlement.

This site documents application SDK use and protocol responsibilities. Operator onboarding, credentials, deployment, and service operation belong in the [repository documentation](https://github.com/bigdreamsweb3/trustlink-pay/tree/main/docs).

## Execution and evidence requirements

The current daemon authenticates through Receiver's wallet challenge/session mechanism, claims verified work and checks Node's signed execution receipt against its pinned public key and the exact execution projection. It dispatches `AUTHORIZED_FUNDING`, `TIN_OPERATION` and `SETTLEMENT`. The [repository transaction map](https://github.com/bigdreamsweb3/trustlink-pay/blob/main/docs/laboratory/cranker-transaction-map.md) gives their complete instructions, accounts, transport and retry boundaries.

Funding broadcasts the unchanged sender-signed TCAP `deposit_private_funding_v1` transaction in `tcap_funded_note_v1` mode. Its payer is already fixed in the signed transaction; the current SDK sets the depositor as payer. Cranker cannot change its blockhash or add fee sponsorship after signing. TIN creation uses Cranker's payer/signature, with owner approval in an Ed25519 instruction, and selects direct or staged legacy transactions at the 1,232-byte limit. Native settlement requires current-lease authorization and Mother co-signing for one TSNP instruction followed by its proof-bound Memo; Cranker pays that transaction's network fee.

Receiver exposes thirteen proof inputs for settlement, with the sealed funding root at index 12 and its readonly account as TSNP account 14. Cranker receives no note opening, note commitment or funding membership path in the credit projection. Matching initialized verifiers and proving artifacts remain prerequisites; source changes do not establish deployed acceptance.

The [November 2 TIN record](https://github.com/bigdreamsweb3/trustlink-pay/blob/main/docs/laboratory/experiments/EXP-20261102-tin-staged-finalization.md) verified six finalized transactions: initializer, four encrypted uploads and finalizer. Its account allocations and stage closure occurred within the final transaction. It did not test native credit, owner recovery or the installed DBrix V1 transport.

The retained Creditcoin settlement branch submits an EVM hub call from its configured executor wallet and waits for a successful receipt and publication event. Receiver's `CONFIRMED` result describes that hub transaction; destination payout requires separate evidence. Epoch payout/refund/reimbursement and verifier/root setup are separate instruction families, outside this daemon's normal dispatcher.

Operators need the configured wallet/registration policy, service access, RPC context and fee funding for the transactions they submit. A worker cannot refresh an owner-signed blockhash or replace a verified recipient transition. After an uncertain submission, reconcile its signature before repeating the work; matching terminal reports are treated idempotently by Receiver under its contract.

Current private credit selects an immutable sealed pool account as `fundingRootAccount`, with its root in proof input 12; later deposits do not invalidate that capture. Before signing, Cranker checks the sealed pool layout, asset/token/source counts and release. Recognized shared-root, epoch, route, pool-capture or authorization-expiry conflicts require fresh Node verification through the authenticated current-version retry; a saved signature requires reconciliation. Receiver independently enforces lease ownership/expiry and original confirmed funding lineage for credit. The retained Creditcoin settlement branch remains separate, and verifier initialization stays outside the daemon dispatcher.

Use the [existing operator runbook](https://github.com/bigdreamsweb3/trustlink-pay/blob/main/docs/CRANKER-OPERATOR-GUIDE.md), [Cranker implementation record](https://github.com/bigdreamsweb3/trustlink-pay/blob/main/docs/laboratory/components.md) and [lifecycle guide](/developers/payment-intent-lifecycle). The daemon reports terminal `CONFIRMED` or `FAILED`; its `tx sent` log is not a Receiver `SUBMITTED` transition. A later report/read failure cannot undo a successful chain transaction, so reconcile known signatures before retrying.

## Native submission transport

Current native settlement uses pinned Kit 8.5.0 to preserve the V1 message, payer/Mother signatures and 4,096-byte limit, then broadcasts once and confirms through bounded HTTP polling. It retains the confirmed blockhash read's context slot as `minContextSlot` for confirmed preflight and block-height polling. The gateway tries another provider with the unchanged request on RPC `-32016` (minimum context slot not reached). A minimum slot excludes lagging banks but does not establish fork agreement or extend blockhash lifetime. Cranker saves the signature, blockhash lifetime and wire hash through authenticated Receiver PUT before broadcasting. A checkpoint failure prevents broadcast; later errors retain signature identity. A signed attempt whose lease expires becomes FAILED for reconciliation rather than automatic rebuild.

The earlier DBrix sender used a root WebSocket URL while the TSN gateway accepts `/ws`. Its HTTP submission happened before socket confirmation, so the socket error did not prove transaction failure. Use finalized receipt reconciliation for an already executed credit; avoid a new deposit or snapshot retry. The replacement sender was checked offline; the November 5 operator log and finalized receipt verify one 3,044-byte funded-note credit using HTTP confirmation. Its Receiver report missed lease expiry; owner recovery remains a separate check.

## Blockhash provider disagreement

The configured gateway retries the unchanged funding request across its providers after a bank blockhash rejection. Cranker retains its exact signed-wire fallback for funding; neither mechanism can repair an expired owner signature. Inspect funding confirmation before another deposit, and preserve a confirmed deposit while recovering its separate settlement. Deployment and initialized matching verifier state are separate execution prerequisites.

If confirmation reporting misses the Cranker lease, the corrected authenticated PATCH validates that exact signed checkpoint and reporting payer against the finalized authorized receipt before updating Receiver. Cranker retries only temporary finality/RPC/report transport failures with the same confirmation body up to six times, with a 25-second request deadline and five seconds between attempts. Mismatched receipts or authorization are not retried. A remaining report failure logs the preserved signature for receipt reconciliation and does not report the confirmed transaction as FAILED. Existing FAILED work needs receipt-only recovery, not another deposit or settlement; see [the November 5 command and evidence](https://github.com/bigdreamsweb3/trustlink-pay/blob/main/docs/references/TSN-OPERATOR-GUIDE-20261105.md#expired-cranker-confirmation-report).

## Native pool timing and attempt recovery

Native hidden-head credit, pool capture and epoch accounting receive a bounded 180-second Cranker lease covering initial Node authorization, Mother co-signing and submission. Node claims and funding/TIN/other-settlement Cranker claims remain 60 seconds. Signing still requires an active current lease; expired unsigned native work needs fresh verification, while a saved signature remains protected for reconciliation.

Cranker recognizes exact HTTP 409 `detail` or `error` values for the guarded native retry reasons, including `TCAP_POOL_CAPTURE_STALE` and the Node’s explicit pre-signing blockhash-expiry rejection. Only native work without a saved signature can request fresh verification, including the pre-checkpoint `TCAP_TRANSACTION_BLOCKHASH_TOO_OLD_FOR_SUBMISSION` rejection when fewer than 20 block heights remain after co-signing. Both selected and observed heights must be positive u64 values; malformed or unavailable reads fail before checkpointing with bounded diagnostics. A refused retry is left for reconciliation and is not overwritten by a FAILED report. Signed transport errors retain their signature and report whether SEND or CONFIRM failed. RPC preflight failures retain numeric RPC/Solana codes, instruction index and custom program error when available; Kit code `7050008` is labeled `transactionError=BLOCKHASH_NOT_FOUND`, not a program error. HTTP failures retain only status, and deadline expiry reports `TIMEOUT`. Provider messages, logs, URLs and transaction bodies are excluded. These diagnostics do not authorize rebuilding signed work.

Pool capture is preparation for credit, not recipient settlement. A separately authenticated `POST /api/internal/node/work/recover-pool` can inspect a FAILED pool attempt whose blockhash lifetime has ended. Recovery requires a finalized height past its recorded lifetime, an invalid blockhash, no receipt/status and an absent canonical immutable pool account read at or after that finalized context. `execute=false` preserves work; explicit `execute=true` archives the checkpoint, clears obsolete execution authorization and returns only pool work to RECEIVED for fresh Node verification. Found execution, live hashes, unavailable/stale RPC or concurrent state changes reject. This does not recover signed credit/epoch work or mark a payment confirmed.
