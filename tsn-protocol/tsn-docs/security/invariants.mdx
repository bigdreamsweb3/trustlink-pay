TSN separates identity, authorization, private-state verification, and asset settlement. These principles describe the intended trust boundaries; availability of a feature still depends on its verified end-to-end implementation.

## Core boundaries

- **The owner authorizes wallet actions.** A service or Cranker cannot change the sender's signed payment terms.
- **GPRU guards private state.** Its proof is intended to show that the hidden user state is current and that the proposed transition follows from it.
- **TCAP governs funds.** It checks accepted assets, authorization, and liquidity, then applies valid changes atomically.
- **A confirmed transaction is the settlement evidence.** Request acceptance, service verification, and transaction submission are earlier stages.

## Limits

Local hidden-head proof/build evidence does not establish completed live credit. Confidential debit and exit remain unverified as end-to-end capabilities. The native-credit proof hides the TIN route and predecessor witness from the on-chain statement, but its amount, asset, shared roots, nullifier, successor point and encrypted Memo remain public. The published nullifier is derived from public deposit data, so funding and credit can be linked. The Node resolves private routing and constructs the witness, so this boundary does not establish owner-only knowledge or immunity to timing and transaction correlation. Direct wallet transfers expose their endpoints; confidential debit and exit require separate execution evidence. See [the privacy limits](/security/threat-model) for the current encoding and trust assumptions.

Do not infer that a capability is active from a helper, diagram, or program instruction alone. Check the target network and verify the transaction and resulting state. Detailed source-level checks and evidence requirements are maintained in the [repository documentation](https://github.com/bigdreamsweb3/trustlink-pay/tree/main/docs).
