# Component engineering records

**Status: CURRENT for inspected native-credit contracts; scope reviewed 2026-11-02.** These records link the important processing functions and their boundaries. The [generated interface reference](interface-reference.md) supplies instruction, account and endpoint discovery; the [SDK reference](../../tsn-protocol/tsn-docs/sdk/api-reference.mdx) supplies exported signatures. Presence in those catalogs does not establish runtime reachability.

## TIP and TIN

TIP owns identity creation, authenticated route data, owner recovery and the shared route-membership root. A TIN is the ten-digit identifier, not a wallet secret. The registry is derived from a keyed lookup commitment; the issuer generates the TIN and the owner authorizes the exact payload. An owner-indexed recovery account holds a wallet-encrypted envelope separately from the registry.

The [TIP state structures](../../tsn-protocol/programs/transfer-identity-protocol/tin-registrar/program/src/state.rs) include `GlobalState`, `TinV1Account`, `TinV1OwnerRecoveryAccount`, `TinV1CreationStaging`, and `TipRouteMerkleRootV1`. Creation validates owner authorization, keyed commitment, envelope lengths, route and policy versions, ElGamal key commitment and the BabyJubjub balance scan key. The [creation handler](../../tsn-protocol/programs/transfer-identity-protocol/tin-registrar/program/src/processor/create_tin_v1.rs) creates the identity/recovery accounts and appends a route leaf. The [staged handler](../../tsn-protocol/programs/transfer-identity-protocol/tin-registrar/program/src/processor/tin_v1_creation_staging.rs) accepts chunked data before finalization when the direct transaction would exceed transport capacity.

`route_leaf` in [route_root.rs](../../tsn-protocol/programs/transfer-identity-protocol/tin-registrar/program/src/route_root.rs) authenticates the ElGamal key, policy and two scan-point coordinates through a five-field Poseidon relation. A newly created registration changes the shared TIP root. A witness snapshot must preserve ordered earlier leaves and match that new root. The earlier November 2 observation found a registration without the new scan key; no owner migration into the current layout was found in the inspected runtime. Current `TinV1Account::VERSION` is 1; global state uses `CURRENT_VERSION=3`. The [later six-transaction run](experiments/EXP-20261102-tin-staged-finalization.md) independently verified fresh registry version 1 with the current creation path.

SDK `resolveTinV1Identity` reads and validates the PDA, owner, version, status, lookup commitment, key and route fields before decrypting the AES-GCM identity envelope. It returns the display identity, `ownerPubkeyHash`, registry and route metadata, or null for a missing account; malformed bindings and ciphertext produce explicit errors. The lookup secret is a trusted backend/issuer/Node concern, never browser configuration. Node performs its own current route resolution for payment verification.

`buildTinV1Creation` prepares encrypted inputs and the owner intent hash. `submitTinV1Creation` posts the signed creation body to `/tin-operations`. It uses fetch directly and does not accept `TsnHttpClient`'s injected fetch option. Cranker chooses direct or staged creation and checks the resulting chain registry. Consult the [five existing issuance stages](../protocol-flows/tin-creation/README.md) for detailed arguments, failure recovery and evidence. TIN identity is not legal identity certification.

## GPRU and the hidden-head prover

GPRU owns verification of routing and hidden state-transition relations; it owns no reserve tokens. Its [hidden-head module](../../tsn-protocol/programs/gpru/src/hidden_head.rs) stores verifier configuration in `GpruHiddenHeadVerifierV1`, including authority, circuit/key commitments, enabled state, Groth16 points and thirteen IC entries. `initialize_verifier` validates the key vector and commitments. `verify_transition` validates canonical public scalars, caller and Memo binding, current TCAP/TIP roots, action commitment and the Groth16 relation before returning success.

The [circuit](../../tsn-protocol/programs/gpru/circuits/hidden_head_v1/main.circom) proves hidden route membership, predecessor head/token membership, transition arithmetic, nullifier insertion and one-time ciphertext binding. Public input count is twelve. The [cryptography record](cryptography.md) documents the ordered fields and why the delta ciphertext relation is necessary.

Node `prove_hidden_head_credit` in [hidden_head_prover.py](../../tsn-protocol/services/tsn-node/hidden_head_prover.py) requires six explicit artifact settings, invokes the Node proving script through a subprocess, and validates the returned proof/key bindings against on-chain verifier bytes. The [Node script](../../tsn-protocol/programs/gpru/circuits/hidden_head_v1/scripts/node-prove.mjs) pins metadata/artifact hashes and verifies generated or supplied Groth16 proofs locally. This arrangement is a local adapter, not evidence of a separately deployed prover HTTP service.

`HiddenHeadWitnessStore.prepare_credit` reads `tip-<root>.json` and `tcap-<root>.json`, validates structure, point/subgroup constraints, collision rules and reconstructed roots, then constructs private witness fields. `finish_credit` incorporates the Memo commitment into the successor state. `save_candidate` publishes an immutable candidate without overwriting a conflicting snapshot. A saved candidate advances no chain state: a later chain read must select its exact root before it is trusted as current.

Missing settings, invalid metadata hashes, unknown roots, stale verifier bytes, oversized transport or failed local proof verification stop preparation. [Focused tests](../../tsn-protocol/services/tsn-node/tests/test_hidden_head_witness.py) exercise reconstruction and proving. A verified development key is not a production trusted-setup ceremony or an independent circuit audit.

## TCAP assets, reserves and commitment state

TCAP governs approved asset policy, reserve/vault relationships, funding liabilities and the shared state root. [state.rs](../../tsn-protocol/programs/tcap-protocol/programs/tcap/src/state.rs) defines global configuration, asset registry and entries, reserve state, commitment root, nullifier records and other instruction-family state. An entry's token ID, decimals, token program, mint, operational/risk status and custody references are authoritative. SDK and Node resolve these values from chain rather than guessing a reserve from an unrelated PDA.

`deposit_asset_v2` transfers the sender-approved amount from the source token account to the governed vault and updates reserve accounting under its policy checks. `credit_gpru_memo_v1::handler` receives a proof, digest, validity slots, old root, next sequence, token, amount and nullifier. It checks global/root/reserve pause state, the active approved asset, canonical reserve relationship, TSNP program and derived authorization signer, pending liability and solvency. It invokes GPRU before any root/liability mutation. Success advances the root and shifts the amount from pending to settled confidential liability; failure rolls back that instruction's mutations.

The credit instruction requires eleven TCAP account positions: payer, config, commitment root, asset entry, reserve, TSNP program, TSNP authorization signer, TIP route root, GPRU verifier, instructions sysvar and GPRU program. These accounts are not interchangeable with older per-TIN tip or one-time-tip state. Its proof argument stores twelve 32-byte inputs and 64/128/64-byte Groth16 A/B/C encodings.

Governance and initialization instructions establish accepted assets, reserve infrastructure and the canonical commitment root. Migration instructions are one-time operational capabilities, distinct from ordinary credit. TCAP's library still exposes debit/exit and one-time-tip families; source presence alone does not establish their use by the current hidden-head services. The [fund-protection guide](../TCAP-FUND-PROTECTION.md) complements this accounting boundary.

## TSNP, Mother Escrow, Settlement DNA and epoch treasury

TSNP is the on-chain protocol program whose crate retains `trustlink_escrow`; TSN names the complete infrastructure. `register_tcap_credit_authorization_v2::handler` requires a signer matching `MotherEscrow.authority`, verifies the argument/proof/digest agreement, derives the TSNP authorization signer PDA and invokes TCAP with signed PDA seeds. It accepts thirteen TSNP account positions and never creates a recipient identity account in the credit call.

`derive_authorization_digest_v2` hashes the domain, commitment-root account, old root, next root sequence, validity slots, amount, token ID and nullifier. Its output authorizes the exact transition context, not an arbitrary future credit. [Mother state](../../tsn-protocol/programs/tsn/protocol/programs/trustlink-escrow/src/tsn/state/mother_escrow.rs) also tracks registration/policy/epoch configuration. A service's Node verification key and Mother's chain authority have different roles even when an operator manages both.

The separate epoch family contains `EpochTreasury`, `EpochSettlementLedger`, `EpochClaimSlot`, `PrivateSettlementConfig`, `CrankerVault` and `SettlementDna`. `tsn_fund_epoch_treasury` and `tsn_accept_intent` are distinct program entrypoints; a builder may combine them atomically where that family requires it. They are not the native TCAP deposit's instruction sequence.

In [execute_private_payout](../../tsn-protocol/programs/tsn/protocol/programs/trustlink-escrow/src/tsn/instructions/execute_private_payout.rs), checks bind Mother configuration, operator/Cranker/vault, epoch treasury and ledger, permit signature, slot, nullifier, amounts and recipient. The payout and reimbursement mutate that family's token and liability state together. [Refund](../../tsn-protocol/programs/tsn/protocol/programs/trustlink-escrow/src/tsn/instructions/refund_epoch_claim.rs) uses its own authorized slot transition. Calling the native hidden-head path a universal reimbursement mechanism would conflate these families.

These entrypoints remain in source despite historical current-flow descriptions. Their production use, complete runtime reachability and every migration precondition require separate verification. See [historical epoch record](../TSN-FINAL-ARCHITECTURE.md) and the [instruction catalog](interface-reference.md).

## Receiver

Receiver is the durable ingress, lease, status and projection service. [receive](../../tsn-protocol/services/tsn-receiver/lib/store.ts) validates external work kind and funding authorization, encrypts the signed funding body for Node, and stores allowlisted coordination fields. Within a database transaction it makes work ID/payload commitment idempotent and pre-creates an internal settlement reference. That reference remains RECEIVED; its Node lease requires confirmed linked funding.

`leaseForNode` and `leaseForCranker` select eligible work under versioned leases; expired leases can be reclaimed. `transition` checks actor, owner, lease expiry and expected state version. Node may report VERIFIED or REJECTED; Cranker may report SUBMITTED, CONFIRMED or FAILED. Matching terminal signatures can make a lost-response report idempotent. `assertNodeVerificationAttestation` verifies the signed input/evidence/execution/lease projection before Node decisions become executable.

`crankerExecutionPayload` strips data outside each work kind's execution allowlist. `publicCoordinationPayload`, [public-view.ts](../../tsn-protocol/services/tsn-receiver/lib/public-view.ts) and work-status handlers expose sanitized coordination and transaction results. Receiver can see ingress before encryption; encryption at durable storage does not make the HTTP ingress operator blind to a submitted payment.

Receiver uses Firebase Admin/Firestore in configured operation and a local JSON-backed Firestore implementation for controlled development. [Storage modes](../team/operations/receiver-storage-modes.md) states the limits. Worker API keys, Node attestation keys and Cranker wallet challenge/session authorization are separate controls. The [Receiver tests](../../tsn-protocol/services/tsn-receiver/tests/work-contract.test.mjs) cover payload boundaries, while node-envelope and local-firestore tests cover other layers. No general per-client rate-limit guarantee was established by this inspection.

## Node

Node is the verification and transition-preparation service. Its [FastAPI server](../../tsn-protocol/services/tsn-node/server.py) provides the application facade and authenticated worker/authorization endpoints. `post_intent` forwards payment ingress to Receiver; it does not itself settle the payment. `receiver_verification_worker` claims RECEIVED work and submits a signed VERIFIED or REJECTED decision.

`_verify_receiver_work` branches on AUTHORIZED_FUNDING, SETTLEMENT and TIN_OPERATION. Funding verification validates canonical sender message/signature, recipient owner hash, token policy, exact owner-signed deposit and simulation. Settlement verification requires confirmed linked funding and constructs the transition. TIN verification checks owner/issuer authorization and serialized private identity inputs. `_sign_node_verification` hashes the allowlisted execution projection expected by Receiver and Cranker.

`_settlement_funding_context` rechecks confirmed deposit content and derives its stable nullifier. `_construct_verified_tcap_transition` reads current TIP/TCAP roots and verifier, reconstructs a witness, encrypts the owner action Memo, enforces transport capacity, proves locally and verifies preconditions again. Only then does it save a candidate and return the execution transition. No private paths, predecessor commitments or raw delta belong in the Receiver decision.

`create_settlement_authorization` checks verified work and active lease before preparing the authorization response. `sign_settlement_transaction` verifies the submitted transaction statement and existing attestation before Mother co-signing. Missing keys/configuration, stale chain state, invalid recipient bindings, failed simulation or proof failures stop these paths. Node persistence is backed by Receiver state APIs where configured; in-memory/local testing modes do not establish multi-node consensus or highly available production storage.

The Node's privacy role is not equivalent to owner-only knowledge: its lookup material, decrypted ingress and witness preparation can expose sensitive information to the authorized verifier. The [Node key guide](../TSN-NODE-KEYS.md) describes credential ownership. [Focused tests](../../tsn-protocol/services/tsn-node/tests/test_payment_intent_recipient_binding.py) exercise recipient binding; threshold access, nonce and route tests exercise distinct contracts.

## Cranker network and operator worker

The inspected [Cranker daemon](../../tsn-protocol/services/tsn-cranker-op-daemon/scripts/cranker.ts) is an operator worker. It establishes Receiver wallet-authenticated sessions, leases verified work, checks Node's Ed25519 attestation, executes the relevant branch and reports signatures/results. A collection of such workers does not by itself prove a deployed permissionless Cranker network.

`processAuthorizedFunding` validates and submits the unchanged signed TCAP deposit, handles configured RPC fallback and confirms the resulting signature. `processSettlement` obtains an authorization matching the active lease, builds the TSNP credit instruction followed by its bound Memo, obtains Mother co-signing and submits through the DBrix Solana V1 path. It then checks that TCAP's shared root advanced to the expected state. `processTinOperation` validates the private creation body and chooses direct or staged instructions by transport size.

The [Cranker transaction map](cranker-transaction-map.md) details all branches and their evidence limits. Node now returns the exact transition with the required authorization kind and current lease ID/version/expiry after reverification. Local tests cover this correction and the guarded retry for missing-snapshot or the exact repaired TCAP asset-preflight rejection; confirmed funding is preserved while Node independently prepares settlement again. Installed DBrix V1 cluster acceptance, native settlement and Creditcoin hub execution remain unverified.

`verifyNodeAttestation` must remain consistent with Receiver's canonical projection. `confirmSignatureViaRpc` implements bounded confirmation polling, not consensus finality beyond its selected commitment. The daemon reports failures but cannot substitute its operator signature for owner funding approval. Cranker sessions, fees and registry policy are operational prerequisites, not application payment identity.

The [operator guide](../CRANKER-OPERATOR-GUIDE.md) contains existing setup procedures. [Attestation tests](../../tsn-protocol/services/tsn-cranker-op-daemon/tests) and the generated SDK catalog describe implementation evidence; live worker availability was not established here.

## SDK, private view and application boundaries

The private workspace package `@trustlink/tsn-sdk@0.1.0` exports client, canonical messages, TIN, authorization, receipts, recovery, device, session, GPRU, cross-chain and program helpers. Its [exports map](../../tsn-protocol/sdks/tsn-sdk/package.json) defines supported import paths. Server modules are explicitly exported; the root barrel must not be presumed browser-safe merely because many client functions are browser-capable.

`TsnHttpClient` supports injected fetch and an optional `x-api-key`; generic post/get/patch methods JSON-encode requests and throw on non-2xx results. It adds no built-in retries or generic timeout. `getTsnNetworkStatus` has a default 2,500 ms probe timeout and prefers a responsive configured local endpoint before a configured live endpoint. Its readiness flag tests service reachability, not verifier installation or settled balances.

`createTcapAssetPaymentAuthorization` reads the registered mint/asset and decimals, then produces the canonical message with UI-denominated amounts. `buildPaymentAuthorizationIntentRequest` checks amount precision, converts to the actual request shape and rejects malformed recipient hashes. The application obtains message and transaction signatures from its wallet; the SDK helpers do not authorize on its behalf.

Device exports use non-exportable WebCrypto credentials and fingerprint helpers. Session and receipt modules bind private requests and proof-of-possession. Private-view exports `configureTsnPrivateValueResolver` and `TsnPrivateValueElement`, a browser element whose resolution depends on configured authorization. Lit web components and the separate `@lit-protocol/*` threshold provider are different technologies; package presence does not prove a deployed threshold action. [Owner balance history](../../tsn-protocol/sdks/tsn-sdk/src/gpru/balance-history.ts) reconstructs validated Memo actions using owner-held scan material and externally supplied history.

The public [SDK handbook](../../tsn-protocol/tsn-docs/sdk/index.mdx) and [full API reference](../../tsn-protocol/tsn-docs/sdk/api-reference.mdx) link exact source signatures. Experimental cross-chain and exit APIs stay exported; tutorials must state their missing execution evidence instead of inventing a complete settlement helper.

## DIP, cross-chain adapters and supporting infrastructure

DIP defines a deposit-ingress boundary. The workspace includes [cross-chain services/contracts](../../tsn-protocol/services/tsn-crosschain), Solidity destination/adaptor contracts, route configuration, liquidity-attestation and exit workers, plus SDK facades. Circle CCTP and Attestcoin are external integrations with their own proof/route assumptions. No generic cross-chain execution guarantee follows from this inventory.

The [RPC gateway](../../tsn-protocol/services/tsn-rpc-gateway/config.mjs) configures HTTP/WebSocket upstreams, origin controls and bounded provider timeouts. It supplies transport; it is not payment authorization or a witness-consistency oracle. The frontend/backend and `protocol-tests/ui` are application/testing surfaces. Evidence capture tools can retain sanitized coordination, confirmed signatures and decoded public state, but should not retain raw private TIN or witness payloads.

Historical/public cross-chain claims need route-specific contract, address, funding, proof and destination confirmation evidence. Existing [cross-chain team records](../team/cross-chain/README.md) preserve observations. The independent [research library](../../research/Trustlink-Research/README.md) is indexed as historical/mixed where its architectural names conflict with the current executable contract.
