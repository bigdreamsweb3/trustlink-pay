**In plain English:** TIP is the Transfer Identity Protocol that manages transfer identities and resolves their payment routes. A TIN is one portable, human-readable 10-digit identity within TIP. A sender can share a TIN and confirm the resolved recipient name before authorizing a transfer, instead of copying a wallet address. The TIN does not hold tokens or replace the owner's wallet authority.

## What TIN is (and is not)

| Wallet address                               | TIN (managed by TIP)                                        |
| -------------------------------------------- | ---------------------------------------------------------- |
| Public cryptographic account identifier      | 10-digit payment identity                                  |
| Identifies a public key or account authority | TIP resolves the route associated with a TIN                |
| May own token accounts                       | Does not itself hold tokens or act as a private key        |
| Usually exposed directly                     | Resolved through TIP route metadata; not itself a wallet key |

TIN is not a private key or token account. A confirmed TIN V1 binds to an owner wallet and encrypted identity data. A sender can use the resolved display name as a payment-confidence check; that name alone is not legal verification or payment authorization.

## Registrar program

<Note>**Status: Live on Devnet.**</Note>

The current TIN V1 registry derives its PDA from a keyed lookup commitment,
not from a public TIN or owner wallet. The trusted issuer and Node share a
high-entropy `TINS_LOOKUP_SECRET`; there is no all-zero public fallback. The
secret is required to derive the commitment and decrypt the identity envelope,
and must never enter a browser, Receiver payload, or Cranker request. The
program records the owner authorization and encrypted identity; it does not
generate the random ten-digit number. The trusted issuer generates the TIN,
checks that its commitment PDA is unused, and submits the owner-authorized
creation through Receiver, Node verification, and Cranker execution.

The current TIP V1 route stores a versioned GPRU ElGamal scan public key and its key commitment, alongside
TIP route and policy commitments. The scan key is public and stable for the route; its matching secret
material stays with the owner. The current TSN credit source invokes GPRU to verify a DNA-key derivation
proof against the TIP registry. The key commitment detects key/version substitution; it is not proof of
ownership or a valid balance transition. TIP source also appends route commitments to a shared route root
used by the GPRU hidden-head Groth16 proof ABI. Node currently cannot produce that proof and fails closed.

Current TIN V1 SDK helpers derive these PDAs:

| Helper | Seeds / derivation |
| --- | --- |
| `getTinV1CreationStagingPda` | `tin-v1-create-stage`, owner key, intent hash |
| `getTinV1OwnerRecoveryPda` | `tin-v1-owner-recovery`, owner key |
| TIN V1 registry PDA | `tin-v1`, keyed lookup commitment |

## Resolution flow

1. The sender supplies the 10-digit TIN to the application.
2. The application requests display identity from the TSN Node resolution
   endpoint; Node derives the registry PDA with its protected secret, validates
   current TIN V1 state, and decrypts the identity disclosure.
3. The SDK builds the sender authorization using the TIN and resolved display
   identity. The sender does not sign a client-supplied route commitment.
4. At payment ingress, Node independently resolves the current on-chain TIN V1
   TIP route and constructs the recipient transition from that route.

Resolution is by requested TIN, not public registry enumeration. The endpoint
returns identity disclosure, never plaintext seeds or child private keys.

## Record classes

| Class              | Examples                                                          | Boundary                                            |
| ------------------ | ----------------------------------------------------------------- | --------------------------------------------------- |
| Public             | Program ID and commitment-derived account address                 | Does not expose a wallet-to-TIN index               |
| Integrity metadata | Owner authorization, route commitments, state version             | Verifiable protocol data, not the plaintext TIN     |
| Encrypted          | TIN and display name envelope; wallet-protected master-seed data   | Ciphertext stored with the registry                 |
| Off-chain app data | Optional profile or notification references                       | Stored under the app's own access policy            |

## Ownership and recovery

The owner wallet authorizes TIN creation. The main TIN registry account stores
an owner commitment and no standalone owner-public-key field. Wallet recovery
is stored separately in an on-chain PDA owned by the TIN Registrar program;
it is not stored in the main TIN registry account. The recovery PDA is derived
from the `tin-v1-owner-recovery` seed and the owner's wallet public key. It
contains that public key and an encrypted TIN recovery envelope. TIN creation
creates and writes both accounts.

When the owner reconnects, the SDK derives the recovery PDA from the connected
wallet, fetches its envelope, and decrypts it locally after a separate
domain-separated wallet signature. The recovery PDA gives the wallet a lookup
path without adding the owner public key as a field in the main registry
account. Previously created master-seed envelopes may still contain an
`ownerPublicKey` property in plaintext; removing it from the SDK affects newly
created envelopes and does not rewrite existing on-chain accounts. The raw
recovery signature, TIN, and display name are not sent to Node or Cranker as
part of recovery.

The recovery locator does not reveal the TIN or derive the registry PDA. The
registry is found through its keyed lookup commitment, while the owner PDA
locates the recovery ciphertext. Registry uniqueness follows from the keyed
commitment PDA; owner uniqueness follows from the recovery PDA. Receiver and
Cranker receive the recovery ciphertext and other encrypted fields.
