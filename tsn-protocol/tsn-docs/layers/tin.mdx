**TIP (Transfer Identity Protocol)** manages transfer identities and their route information. A **TIN (Transfer Identity Number)** is one 10-digit identity within TIP. A TIN gives a sender a recipient identifier to resolve before authorizing a transfer; it is not a wallet key, token account, or balance container.

## Identity and wallet recovery

The TIP registry keeps identity information encrypted. The owner's recovery record is stored in a separate on-chain PDA owned by the TIN Registrar program, not inside the main TIN registry account. That recovery record contains the owner's public key and an encrypted TIN recovery envelope. When the owner reconnects the wallet, the SDK derives the recovery PDA, fetches the envelope, and decrypts it locally.

This separation means the main registry does not need a standalone owner-public-key field to support wallet recovery. Public account addresses and transaction metadata remain visible on Solana, so this design does not make every part of identity activity unlinkable.

## Resolving a recipient

An application can use the TSN SDK to resolve the TIN's owner-provided display name and prepare a payment authorization. The display name is a recipient confirmation aid; it is not legal identity verification. The sending wallet still reviews and signs the payment authorization.

The hidden-head proof flow that is intended to use TIP route information is not established as an end-to-end settlement capability. See the [SDK identity guide](/developers/private-tin-issuance) for application-level usage. Issuer operations and the registry's exact data contract belong in the [repository documentation](https://github.com/bigdreamsweb3/trustlink-pay/tree/main/docs).
