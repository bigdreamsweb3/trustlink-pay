This guide walks you through your first application integration with the Transfer Settlement Network (TSN). You will install the SDK, check service availability, resolve a Transfer Identity Number (TIN), construct a signed payment intent, submit it through the SDK, and observe the work lifecycle. TSN is a Solana-first settlement coordination layer. The live path uses credit-only TCAP tips, not public payout accounts.

## Prerequisites

Before you start, make sure you have:

- Solana CLI installed and configured for Devnet
- A Solana wallet with Devnet SOL
- The canonical `@trustlink/tsn-sdk` package
- A browser wallet that supports message signing

TSN Receiver, Node, and Cranker are operator-run services. As an integrator,
you use the SDK façade; your application does not import TCAP/TIN program
clients or construct raw settlement instructions.

## Step-by-step

<Steps>
  <Step title="Install tooling and set environment variables">
    The TSN SDK is currently a private workspace package; it is not published to the public npm registry. From the repository root, install and build the canonical SDK:

    ```bash title="Install the local SDK"
    npm --prefix tsn-protocol/sdks/tsn-sdk install
    npm run tsn:sdk:build
    ```

    Configure the Devnet endpoints for your integration:

    ```bash title="Environment variables"
    export TSN_RPC_URL=https://tsn-rpc-gateway.vercel.app
    export TSN_RECEIVER_URL=https://tsn-receiver-kappa.vercel.app
    export SOLANA_CLUSTER=devnet
    ```

  </Step>
  <Step title="Check the TSN network before signing">
    Let the SDK select local Node and Receiver services first and their live
    services second. Solana requests always use the configured TSN RPC gateway.
    Do this before preparing a payment and again before requesting a wallet
    signature.

    ```ts title="SDK service gate"
    import { getTsnNetworkStatus } from "@trustlink/tsn-sdk";

    const network = await getTsnNetworkStatus({
      local: {
        node: "http://127.0.0.1:8000",
        receiver: "http://127.0.0.1:8010",
      },
      live: {
        node: process.env.TSN_NODE_URL ?? null,
        receiver: process.env.TSN_RECEIVER_URL ?? "https://tsn-receiver-kappa.vercel.app",
        rpc: process.env.TSN_RPC_URL ?? "https://tsn-rpc-gateway.vercel.app",
      },
    });

    if (!network.readyForTransactions) {
      throw new Error("TSN services are not ready");
    }
    ```

    A gateway failure blocks Solana actions rather than switching to another
    RPC. Cranker availability comes from the Node heartbeat-backed route response;
    a Cranker is a worker, not a public application HTTP service.

  </Step>
  <Step title="Obtain or resolve a TIN">
    A TIN is issued by a trusted TIN V1 issuer; the program does not generate TINs. Issuance requires an owner-signed intent, an issuer HMAC proof, and a protected lookup secret configured on the issuer and Node. See [Private TIN issuance](/developers/private-tin-issuance) for the service boundary.

    For an existing TIN, use the Node resolution endpoint for the user-approved display identity. The sender authorization contains the TIN and resolved display identity; the Node independently resolves and validates the current TIP route from on-chain TIN V1 state. Do not resolve a legacy TIN account with the retired SDK resolver or include route commitments in the sender's authorization message.

    ```ts title="Resolve a TIN through TSN Node"
    const response = await fetch(
      `${process.env.TSN_NODE_URL}/tin-resolution/${encodeURIComponent(recipientTin)}`,
      { headers: { accept: "application/json" } },
    );
    if (!response.ok) throw new Error("TIN could not be resolved");
    const recipient = await response.json();
    ```

    The lookup secret never leaves the trusted issuer/Node boundary. The encrypted identity and owner-recovery envelopes remain encrypted in Receiver work and on-chain account data.

  </Step>
  <Step title="Construct and sign a payment authorization locally">
    The signed message binds the sender, recipient TIN and resolved display identity, amount, fee, nonce, expiry, and the TCAP deposit funding mode. The recipient route commitment is not supplied by the sender; Node resolves and verifies it from the current TIN V1 account.

    ```ts title="Build and sign the canonical authorization"
    import { createPaymentAuthorization } from "@trustlink/tsn-sdk";

    const authorization = createPaymentAuthorization({
      senderWallet,
      senderIdentity: senderWallet,
      receiverIdentity: `tin:${recipientTin}`,
      recipientDisplayName: recipient.displayName,
      recipientDisplayNameSource: recipient.displayNameSource,
      recipientVerifiedCredentials: recipient.verifiedCredentials,
      tokenMintAddress,
      amount,
      senderFeeAmount,
      totalTokenRequiredUi: amount + senderFeeAmount,
      fundingMode: "tcap_deposit_v2",
    });
    const signature = await wallet.signMessage(
      new TextEncoder().encode(authorization.message),
    );
    ```

    The wallet must also sign the TCAP wallet deposit transaction. Do not use legacy wallet-only, PRU, or mixed-funding modes; the live Node accepts only `tcap_deposit_v2`.

  </Step>
  <Step title="Submit the authorized funding work">
    Build the intent request from the signed message and signed deposit transaction, then submit it to the TSN Node `/intents` ingress. The Node forwards it to Receiver; do not post directly to Receiver or expose its service key in browser code.

    ```ts title="Build and submit a current intent"
    import {
      TsnHttpClient,
      buildPaymentAuthorizationIntentRequest,
    } from "@trustlink/tsn-sdk";

    const request = buildPaymentAuthorizationIntentRequest({
      paymentId,
      recipientHash: recipientTin,
      recipientTin,
      tokenMintAddress,
      senderWallet,
      senderAuthorizationMessage: authorization.message,
      senderAuthorizationSignature: Buffer.from(signature).toString("base64"),
      senderAuthorizationNonce: authorization.nonce,
      senderAuthorizationIssuedAt: authorization.issuedAt,
      senderAuthorizationExpiresAt: authorization.expiresAt,
      senderFeeAmount,
      senderSignedFundingTransaction,
      senderFundingMode: "tcap_deposit_v2",
      senderTokenAccount,
      amount,
      source: "my-tsn-app",
    });
    const client = new TsnHttpClient({ baseUrl: process.env.TSN_NODE_URL! });
    const intent = await client.postIntent(request);
    console.log(intent.id, intent.status);
    ```

    The Receiver records work as `RECEIVED`; the response `id` is the stable work identifier. Node independently verifies the authorization, TIN V1 identity, TIP route, and deposit before a Cranker can lease it.

  </Step>
  <Step title="Observe the work lifecycle">
    The internal Receiver state machine is:

    ```text
    RECEIVED -> NODE_VERIFYING -> VERIFIED -> CRANKER_LEASED -> SUBMITTED -> CONFIRMED
    ```

    Node services can list payment work with authenticated `GET /intents`. The public view maps active internal states to `pending`, `REJECTED` to `canceled`, and `CONFIRMED` to `executed`; use `receiverStatus` when you need the raw state. There is no public `GET /intents/:id` endpoint in the current Receiver.

  </Step>
  <Step title="Confirm on Solana">
    Once `receiverStatus` reaches `CONFIRMED`, read the returned transaction signature and verify it on Solana Explorer (Devnet cluster):

    ```bash
    solana confirm -ud <transaction_signature>
    ```

    The on-chain program enforces the commitment, lease, nullifier, and expiry.

  </Step>
</Steps>

<Info>
  The Stable-TCAP faucet is Devnet-only and valueless. It is not USDC or any
  production stablecoin. Historical TCAP ID placeholders are not valid Solana
  public keys; obtain the deployed ID before constructing TCAP instructions.
</Info>
