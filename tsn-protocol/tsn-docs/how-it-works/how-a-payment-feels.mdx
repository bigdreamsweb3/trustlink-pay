title: "A TIN Credit: User and Protocol Steps"
sidebarTitle: "Payment Experience"
description: "What sender, Receiver, Node, Cranker, and Solana each do in the current TIN credit source path."
---

The sender enters a TIN, reviews the identity information returned for that request, and signs payment and reserve-funding details. Receiver accepts the ingress. Node verifies the signed request, resolves TIP route data, and prepares authorized work. A Cranker submits the authorized transaction. On chain, TSN calls GPRU's key and encrypted-credit checks, then TCAP advances its shared global root.

```text
Sender signs intent and funding
  → Receiver stores ingress
  → Node verifies and resolves TIP
  → Cranker submits authorized work
  → TSN invokes GPRU credit validation
  → TCAP advances the shared global root
  → encrypted Memo remains in transaction history
```

The current credit path does not use the hidden-head Groth16 instruction. It does not persist a per-TIN latest ciphertext, so the shared root does not prove that a supplied TIN predecessor is the latest. A confirmed reserve funding transaction does not prove the TCAP transition confirmed.

GPRU and TCAP source separately contain a hidden-head proof path, but current Node, SDK, and Cranker callers do not use it. Its circuit does not prove balance arithmetic, debit affordability, or solvency, and its instruction ABI exposes action kind, token ID, and amount. The common TCAP root remains visible and creates protocol-level linkage.
