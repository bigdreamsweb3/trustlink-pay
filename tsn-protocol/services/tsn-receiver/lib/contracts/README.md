# Receiver work contracts and projections

**Current staged funding, November 18, 2026.** Initial message-only validation forbids signed wire/context, while completed-ingress validation is used only after guarded attachment. The immutable initial commitment remains separate from the completed funding commitment. `FUNDING_READY` has no Cranker execution payload; its private preflight is encrypted. Staged public status exposes only phase/version, readiness boolean/expiry and initial commitment. Exact signed attachment and confirmed receipt lineage preserve their own identities; historical record reconstruction remains separate from new ingress.

These components preserve the existing ingress validation, canonical commitments, compact and legacy verification reconstruction, execution/authorization privacy projections and public intent contract. The flat `../work-contract.ts` and `../public-view.ts` modules remain stable named export interfaces; each implementation file owns one authored function, and model/constants modules are function-free.

`kinds/` owns work-kind checks, `validation/` owns ingress and durable-field validation, `commitments/` owns the unchanged locale-based canonical representation, `verification/` owns compact evidence and reconstruction, `recovery/` owns exact-context nonexecution guards, `creation/` owns initial work records and `projection/` owns caller-specific views. The shared allowlist predicate receives the actual caller-owned set rather than importing service state. Work creation accepts a narrow clock/identity port whose native defaults preserve existing calls.

Existing Receiver work-contract, lease, private coordination, retry, reconciliation and failed-settlement tests verify these contracts through their original facades. Receiver-local verification documentation records suite results and gaps; static links do not establish measured per-function coverage or hosted/chain execution. Error strings, nested allowlists, canonical bytes, stored-record reading and public result override ordering are retained. This package initializes no Firebase, HTTP or chain service.

The subsequent signed-funding context repair adds [exact tuple validation](validation/assert-sender-funding-blockhash-context.ts) to ingress and funding execution projection. `senderFundingBlockhashContext` has only `blockhash`, `lastValidBlockHeight` and `contextSlot`; validated Node evidence preserves all three in the execution commitment. Original ingress context remains encrypted, public projections omit it, and confirmed receipt compaction removes it from execution evidence with the signed wire. Missing older execution context fails closed without blocking separate confirmed-funding lineage reads. [Focused tests](../../tests/funding-blockhash-context.test.mjs) cover canonical numbers/hash, extra-field refusal, privacy/compaction and commitment changes; the [verification record](../../docs/verification.md) identifies their bounded source checkpoint.
