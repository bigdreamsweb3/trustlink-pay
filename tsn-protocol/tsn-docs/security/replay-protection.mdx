# Replay protection

The current TSN credit instruction calls TCAP `credit_gpru_memo_v1`. TCAP requires the supplied previous global root to match `TcapCommitmentRootStateV1.current_root` and the supplied root sequence to equal the stored sequence plus one. A successful transition updates the root and sequence in the same instruction. Resubmitting the same transition with its stale root and sequence fails.

The Node also derives a funding-bound commitment and TSN includes it in the authorization. This binds the settlement authorization to the signed deposit. It is not a separate spent-funding registry.

## Per-TIN latest state is not established by that root

The root is one shared TCAP account, not an authenticated per-TIN balance head. GPRU validates the predecessor ciphertext supplied with the current credit instruction but does not persist an authoritative per-TIN latest ciphertext in that path. A fresh global root and authorization therefore do not by themselves prove that a caller selected the latest predecessor for a particular TIN.

## Hidden-head verifier source

GPRU and TCAP source contain a separate hidden-head Groth16 verifier and root-advance instruction. The active TSN/Node/SDK/Cranker flow does not call them. The circuit/proving workflow has not been demonstrated end to end, and its public instruction ABI exposes action kind, token ID, and amount. All transitions would still touch the same shared TCAP root, which exposes global ordering and protocol-level linkage.

## Safe retry behavior

If a transaction has not confirmed, check its signature and the current global TCAP root before retrying. If it confirmed but the response was lost, do not assume failure from a client timeout. Check the transaction and account state first. A replacement authorization must be based on verified funding and current program state; do not fabricate a new predecessor or replay nonce.
