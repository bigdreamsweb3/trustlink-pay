# GPRU and TCAP state

GPRU verifies cryptographic relations; TCAP governs assets and reserve state. TIP manages transfer identities and route metadata. A TIN is one 10-digit Transfer Identity Number within TIP. The source currently contains a wired credit-transition path and a separate hidden-head proof path that has not been connected to settlement callers.

## Credit transition in the current TSN source

The TSN `register_tcap_credit_authorization_v2` instruction verifies authorization and the GPRU DNA-key proof, invokes GPRU `apply_credit_transition_v1`, and then invokes TCAP `credit_gpru_memo_v1`. GPRU validates the initial ciphertext against the funded amount or checks later ElGamal addition against a supplied predecessor ciphertext. TCAP validates the asset, authorization signer, validity window, predecessor shared root, and next global sequence before advancing that root. The transition binds the Memo instruction data by commitment.

TCAP's shared commitment root is one global account, not a latest-head account for each TIN. GPRU does not persist a per-TIN head in this wired credit path. As a result, this path does not independently prove that a supplied predecessor ciphertext is the latest ciphertext for its TIN. The Memo is stored in transaction instruction data, not in a TCAP balance PDA; historical balance reconstruction requires reading the relevant transactions through RPC or an indexer.

## Hidden-head verifier source

GPRU also contains a Groth16 verifier instruction and Circom source for a hidden route-and-asset head update, sequence increment, Memo/action binding, and one-time nullifier update. The circuit's public inputs are the old and new shared TCAP roots, Memo commitment, action commitment, nullifier, and TIP route-membership root. Private witnesses contain route membership, the prior head, and sparse-map paths. TCAP contains `advance_gpru_hidden_head_v1`, which checks its root and global sequence, verifies asset and authorization conditions, invokes GPRU, and advances the same shared root.

The Node, SDK, Cranker, and active TSN credit instruction do not call this hidden-head path. The repository does not establish a compiled circuit, generated proving/verifying keys, a proof-generation pipeline, initialized verifier account, or end-to-end transaction evidence. This proof source must not be described as live or production-ready.

## What the hidden-head proof does not prove

The circuit does not prove homomorphic balance addition or subtraction, debit affordability, a non-negative balance, or reserve conservation. The current hidden-head instruction arguments include public action kind, token ID, and amount; those values are visible in the transaction. A Memo commitment binds the Memo bytes but does not prove that encrypted contents encode a valid balance.

The design uses one writable TCAP shared-root PDA. Every transition using that path references the same account and advances a global sequence, so public observers can see a shared protocol-level link and ordering. The proof is intended to hide which TIN head changed; it does not provide zero linkability.

## Debit and exit status

TCAP retains older per-TIN tip instructions and debit/exit code paths. The current TSN/Node/SDK/Cranker settlement path does not use the hidden-head proof for debit or exit. The hidden-head circuit does not supply the required balance-sufficiency, subtraction, exit-destination, or solvency proofs. Do not treat these paths as enabled based on the existence of verifier code.
