Receiver coordinates accepted work, Node verification, Cranker leases and result reporting. It pre-creates linked settlement work at funding ingress but permits its Node verification only after confirmed funding. Its database state is coordination evidence; successful Solana execution establishes the corresponding funding or settlement change. Read the [payment lifecycle](/developers/payment-intent-lifecycle) before diagnosing an apparently accepted payment.

## Funded-note privacy boundary

Native ingress requires `senderFundingMode: "tcap_funded_note_v1"`, the exact owner-signed funded deposit and restricted `fundingNote` material containing version 1, secret, blinding and commitment. Receiver validates canonical scalar encodings and the sender signature, then retains this material only in the encrypted Node envelope. Node checks the private opening against the signed approval and deposit. Public coordination and Cranker funding views omit that opening; Receiver's ingress operator can still observe the original HTTP body.

The settlement projection contains the canonical global `fundingRootAccount` and thirteen proof inputs, with the funded root at index 12. It excludes note commitment, secret, blinding and membership paths. Receiver sanitizes the authorization transition and nested proof fields, then requires its public commitment to match verified work before storing it. Funded-tree/verifier setup and fresh proving artifacts must match this source contract; source and offline checks do not establish a deployed credit.

## Storage and configuration

The implementation selects local storage only when both `TSN_RECEIVER_STORE=file` and `TSN_ALLOW_LOCAL_JSON_STORE=true`. `TSN_RECEIVER_LOCAL_FILE` selects the local JSON file. Firebase operation requires `FIREBASE_PROJECT_ID`, `FIREBASE_CLIENT_EMAIL` and `FIREBASE_PRIVATE_KEY`; configure those server-side through the deployment environment. The local implementation supports controlled development and does not establish shared, multi-process production durability.

`TSN_RECEIVER_COLLECTION` and `TSN_RECEIVER_STATE_COLLECTION` identify work and Node state collections. `TSN_RECEIVER_NODE_API_KEY` authenticates Node work/state requests. `TSN_NODE_VERIFICATION_PUBLIC_KEY` verifies Node decisions, while `TSN_RECEIVER_NODE_PAYLOAD_KEY` protects stored Node envelopes. These roles are separate: an API key does not make a decision signature valid. Node primary/fallback URLs, the selected RPC and existing program ID must agree with the worker and chain configuration.

Use the existing [environment example](https://github.com/bigdreamsweb3/trustlink-pay/blob/main/tsn-protocol/services/tsn-receiver/.env.example) for variable names and the [storage-mode runbook](https://github.com/bigdreamsweb3/trustlink-pay/blob/main/docs/team/operations/receiver-storage-modes.md) for deployment constraints. Example URLs and IDs describe configuration, not verified current availability. Keep private keys, payload keys and service tokens out of browser builds and logs.

## Observe and diagnose

After repairing root-selected snapshots, the TCAP asset-layout preflight or the obsolete Node Memo-length guard, `POST /api/internal/node/work/retry` can requeue a settlement rejected with `GPRU_HIDDEN_HEAD_WITNESS_UNAVAILABLE:`, the exact asset reason `TCAP settlement asset is unavailable or its reserve binding is invalid`, the exact funded-root reason `TCAP_FUNDING_ROOT_CHANGED_BEFORE_SETTLEMENT`, or the former Node validation error `GPRU transaction record is missing its twelve public hidden-head inputs`. It requires `TSN_RECEIVER_NODE_API_KEY` and JSON `{id, expectedVersion}`. Receiver requires the original confirmed funding, deterministic settlement lineage and unchanged payload commitment, rejects execution state or other rejection reasons, preserves the rejection in `retryHistory` and wakes Node for fresh independent verification. The endpoint never requeues funding. Its local isolated-store/authentication tests passed; a live recovery submission remains unverified.

The current private credit uses an immutable sealed funding pool; later deposits do not invalidate it. Exact allowed HTTP 409 shared-root, pool-capture, epoch, route or authorization-expiry conflicts can return unsigned native work to RECEIVED through authenticated current-version retry. Credit retries also require confirmed original funding, immutable lineage and funded-proof format. A matching active owner/lease and absence of execution state remain mandatory. Fresh verification keeps the same note and deterministic nullifier; saved signatures require reconciliation.

The root utility `scripts/retry-settlement-snapshot.py` covers the allowed repaired verification reasons, defaults to read-only inspection and reads the configured Node credential without printing it. Adding `--execute` explicitly requeues settlement and can lead to Cranker submission. Reconcile known signatures before recovery, load corrected services and preserve confirmed funding; do not edit the live JSON store or deposit again to repair settlement verification.

`GET /api/health`, `GET /api/work` and `GET /api/work-status/[id]` provide health or sanitized coordination views. Retain work ID, status, state version, reason and transaction signature when diagnosing failures. Avoid exporting the raw database or decrypted Node payload. A healthy process does not imply that the prover, recipient schema or chain accounts are ready.

Node workers lease through `/api/internal/node/work`; Crankers authenticate through their wallet challenge/session flow and claim through `/api/cranker/work`. Receiver checks the signed Node execution projection before verified work is executable. Cranker lease requests have a specific implemented rate limit; this does not imply that every public Receiver endpoint has the same protection. Read [the service API boundaries](/api-reference/services) for request/error behavior.

Node work PUT renews only an unexpired NODE_VERIFYING claim whose owner, work version, lease ID and lease version match. Renewal extends the 60-second expiry and preserves the signed decision context; it cannot revive a completed, expired or reassigned claim. Load the corrected Node and Receiver together so long proof generation can renew its claim. Expired active claims can be reclaimed by normal leasing; this is separate from the guarded retry of REJECTED settlement.

For an HTTP 409, check expected state version, lease owner/expiry and the Node attestation projection against current source. Do not turn a rejected decision into VERIFIED by editing stored state. For missing funding confirmation, inspect the original chain signature before reconstructing work; a sender-signed deposit with an expired blockhash needs fresh sender approval. A shared balance-root change or later funded-tree append requires Node to prove against the current roots using the same funded note and nullifier.

## Upgrade and recovery

Preserve durable work and configured identities during upgrades. Reconcile Receiver's payload/attestation projection with Node and Cranker before switching worker versions; compare current root/verifier settings separately from application deployment. Keep any owner schema migration as an explicitly reviewed one-time operation. Never interpret an old local store as proof of the newly deployed program's state.

If a restart is required, take an appropriate protected storage backup and preserve unresolved signatures for reconciliation. A local store reset discards coordination history and belongs to a controlled development procedure, not routine payment recovery. The [internal operations record](https://github.com/bigdreamsweb3/trustlink-pay/blob/main/docs/laboratory/operations-and-verification.md) defines the evidence needed for the first post-upgrade credit.

## Signed attempts and failed receipt recovery

Cranker saves a signed native settlement identity through authenticated work PUT before broadcasting. Receiver preserves the lease generation and prevents replacement identity. Once an attempt is recorded, lease expiry becomes FAILED for signature reconciliation rather than automatically making the settlement executable again.

A FAILED receipt can describe an already finalized transaction. The current Node-service-authenticated receipt validator matches thirteen proof inputs, fourteen TSNP accounts, both signatures, exact instruction/Memo, canonical funded-root account and TCAP transition root. It does not require today's funded-tree root to equal an earlier successful proof's root. Preview leaves storage unchanged; execution updates only the receipt and archives the earlier error, without signing, submission, requeue or refund. The [November 2 recovery record](https://github.com/bigdreamsweb3/trustlink-pay/blob/main/docs/laboratory/cranker-transaction-map.md#later-november-2-checkpoint-finalized-credit-with-a-failed-service-receipt) is historical evidence for the earlier twelve-input credit, separate from validation of the funded-note contract. See [service contracts](/api-reference/services).

Authenticated Cranker CONFIRMED PATCH can repair an expired native lease's receipt only after matching the durable signed checkpoint, reporting payer and original authorization/lease generation to finalized chain execution. It also admits the immediately reclaimed FAILED version while preventing replacement attempts or changed authorization. The Cranker retries temporary finality/RPC/report transport failures with the same body up to six times, with a 25-second deadline and five-second delay; receipt/authorization mismatches remain errors. A remaining report failure leaves a pending receipt and retains its signature. Load corrected Receiver and Cranker together; the [November 5 reference credit](https://github.com/bigdreamsweb3/trustlink-pay/blob/main/docs/references/TSN-OPERATOR-GUIDE-20261105.md#expired-cranker-confirmation-report) finalized before its original report missed expiry. Manual receipt repair and owner recovery remain separate operator steps.

## Native pool timing and attempt recovery

Native hidden-head credit, pool capture and epoch accounting receive a bounded 180-second Cranker lease covering initial Node authorization, Mother co-signing and submission. Node claims and funding/TIN/other-settlement Cranker claims remain 60 seconds. Signing still requires an active current lease; expired unsigned native work needs fresh verification, while a saved signature remains protected for reconciliation.

Cranker recognizes exact HTTP 409 `detail` or `error` values for the guarded native retry reasons, including `TCAP_POOL_CAPTURE_STALE` and the Node’s explicit pre-signing blockhash-expiry rejection. Only native work without a saved signature can request fresh verification, including the pre-checkpoint `TCAP_TRANSACTION_BLOCKHASH_TOO_OLD_FOR_SUBMISSION` rejection when fewer than 20 block heights remain after co-signing. A refused retry is left for reconciliation and is not overwritten by a FAILED report. Signed transport errors retain their signature and report whether SEND or CONFIRM failed, with sanitized local reason codes.

Pool capture is preparation for credit, not recipient settlement. A separately authenticated `POST /api/internal/node/work/recover-pool` can inspect a FAILED pool attempt whose blockhash lifetime has ended. Recovery requires a finalized height past its recorded lifetime, an invalid blockhash, no receipt/status and an absent canonical immutable pool account read at or after that finalized context. `execute=false` preserves work; explicit `execute=true` archives the checkpoint, clears obsolete execution authorization and returns only pool work to RECEIVED for fresh Node verification. Found execution, live hashes, unavailable/stale RPC or concurrent state changes reject. This does not recover signed credit/epoch work or mark a payment confirmed.
