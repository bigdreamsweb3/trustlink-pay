sidebarTitle: "TIN"

---

**In plain English:** TIN is a portable, human-readable 10-digit payment identity. A sender shares the TIN and can confirm the resolved recipient name before authorizing a transfer, instead of copying a long wallet address. The TIN routes a payment; it does not hold tokens or replace the owner's wallet authority.

## What TIN is (and is not)

| Wallet address                               | TIN                                                        |
| -------------------------------------------- | ---------------------------------------------------------- |
| Public cryptographic account identifier      | Payment identity and route-discovery identifier            |
| Identifies a public key or account authority | Resolves permitted payment routing metadata                |
| May own token accounts                       | Does not itself hold tokens or act as a private key        |
| Usually exposed directly                     | Binds to the TCAP relationship and encrypted snapshot path |

TIN is not a private key or token account. A confirmed TIN V1 binds to an owner wallet and encrypted identity data. A sender can use the resolved display name as a payment-confidence check; that name alone is not legal verification or payment authorization.

## Registrar program

<Note>**Status: Live on Devnet.**</Note>

The current TIN V1 registry derives its account from a keyed lookup commitment,
not from the public TIN number or owner wallet. This prevents public observers
from deriving it directly from either value. The universal issuer deliberately
uses a public all-zero lookup value, so observers can still enumerate TIN/name
records by testing the 10-digit space. That tradeoff enables open universal
resolution; it does not by itself reveal a transfer or settlement history.
The program records the owner authorization and encrypted identity; it does not
generate the random ten-digit number. The trusted XP issuer generates the TIN,
checks uniqueness, encrypts the identity, and submits the owner-approved
commitment through Receiver, Node, and Cranker processing.

The TIN Registrar exposes deterministic PDA helpers rather than a large instruction surface:

| Helper                         | Seeds / derivation                                             |
| ------------------------------ | -------------------------------------------------------------- |
| `tin_v1_pda`                   | `tin-v1`, keyed lookup commitment; not raw TIN or owner key    |
| `tin_v1_creation_staging_pda`  | `tin-v1-create-stage`, owner key, intent hash                  |
| `tin_mutation_staging_pda`     | `tin-mutation-stage`, owner key, intent hash                   |
| `registry_pda`                 | Legacy numeric-TIN registry layout; not the current TIN V1 PDA |
| Other identity / escrow helpers | Legacy account layouts                                         |

## Resolution flow

1. Sender supplies a 10-digit TIN to a trusted resolver.
2. The resolver derives the keyed registry address using protected issuer lookup material and reads the TIN V1 account.
3. The TSN SDK returns the identity disclosure and active GPRU/TCAP route data to the authorized application.
4. The recipient route commitment is bound into the sender's signed transfer intent.
5. The recipient owner wallet provides any required authorization locally.

Resolution must not return plaintext seeds, child private keys, or an unrestricted wallet-to-person mapping. Registrars apply non-enumeration, rate limiting, revocation, and state-version checks.

## Record classes

| Class              | Examples                                                          | Boundary                                            |
| ------------------ | ----------------------------------------------------------------- | --------------------------------------------------- |
| Public             | Program ID and commitment-derived account address                 | Does not expose a wallet-to-TIN index               |
| Integrity metadata | Owner authorization, route commitments, state version             | Verifiable protocol data, not the plaintext TIN     |
| Encrypted          | TIN and display name envelope; wallet-protected master-seed data   | Ciphertext stored with the registry                 |
| Off-chain app data | Optional profile or notification references                       | Stored under the app's own access policy            |

## Ownership and recovery

The user's wallet owns and authorizes the TIN identity: creation is owner
approved, the registry binds to that owner, and the owner key authorizes
wallet-controlled actions. Reconnecting the owner wallet should restore and
display the TIN without requiring the owner to remember or re-enter its ten
digits. The default universal issuer must enforce one TIN per owner.

The current privacy design deliberately does not derive a public registry
address from the owner wallet. A TIN V1 registry is found through its lookup
commitment using the TIN and namespace lookup value. The universal value is
public; issuer-specific values may be private. The
current SDK/XP does not yet implement wallet-only recovery, and the current
creation path does not enforce one TIN per owner. These are recovery and
uniqueness gaps, not a transfer of ownership. A private owner-bound recovery
record or equivalent lookup mechanism must prove wallet control, recover the
identity, and prevent duplicate issuance without publishing plaintext TINs.
The all-zero 32-byte genesis value may identify the public universal issuer
namespace; it must not be used as the lookup secret. Receiver, Node, and
Cranker continue to receive only commitments and encrypted fields.
