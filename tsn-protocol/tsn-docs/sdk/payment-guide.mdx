---
title: "Prepare a wallet-authorized TIN credit"
description: "Real SDK message, deposit and intent construction with explicit signing and settlement boundaries."
---

A native TIN credit uses two approvals separated by Node verification. The sender first signs the canonical payment message. Receiver stores that intent, and Node verifies its authorization, recipient, registered asset and advisory wallet balance. The application then shows “Ready to approve funding”; an explicit approval obtains a fresh blockhash and asks the wallet to sign the exact TCAP deposit. Both approvals bind the same funding-note commitment. Initialized global funding-root state and the thirteen-input verifier remain prerequisites; source and offline checks do not establish live payment activation.

## Resolve the display identity and owner hash

In a trusted lookup environment, use `resolveTinV1Identity`. Verify the returned identity before preparing payment. Keep lookup credentials on that trusted side and return only appropriate display/commitment information to the application. The request's `recipientHash` is the resolved `ownerPubkeyHash`, a 64-character hexadecimal value. Passing the ten-digit TIN there fails request validation.

## Prepare the message

Create a private `FundingNoteV1` with `createFundingNoteV1()` before approval. Keep its secret and blinding in sender memory, pass only `fundingNote.commitment` to the authorization as `fundingNoteCommitment`, and use `fundingMode: "tcap_funded_note_v1"`. The canonical message includes `Funding Note Commitment`; the opening must be excluded from application logs, public receipts and persistent browser storage. See the [funding note API](/api-reference/sdk/modules/gpru-funding-note) for validation and field constraints.

The complete [authorization example](https://github.com/bigdreamsweb3/trustlink-pay/blob/main/tsn-protocol/tsn-docs/sdk/examples/authorization.ts) uses real SDK functions and explicit input types. `prepareIntent` returns the message, nonce, expiry and a `withWalletApproval(signature)` callback for the message-only request. Funding completion is separate and retains that exact request. Synthetic signatures and contexts used to verify examples are not live payment or RPC evidence.

For a live asset, use `createTcapAssetPaymentAuthorization` rather than guessing mint decimals or token ID. It reads the mint and governed TCAP asset entry, validates active deposit policy and returns message plus resolved asset metadata. The pure example assumes those asset facts were already resolved by the application; it does not certify supplied token facts.

## Submit the intent and wait for verification

Call `buildPaymentAuthorizationIntentRequest` with the signed message, resolved `recipientHash`, token/decimals, UI amount, fee, `senderFundingMode: "tcap_funded_note_v1"` and matching private `fundingNote`. Initial requests reject a funding wire or blockhash tuple. Send the request through the configured protected ingress; Node forwards it to Receiver's encrypted-at-rest restricted work store. This records `AUTHORIZED_FUNDING` in phase `AUTHORIZATION`, without creating settlement or making work executable by Cranker.

Show a verification wait state and retain the same payment ID, message, signature, nonce, amount and private note. Receiver status becomes `FUNDING_READY` only after a signed Node readiness decision. `waitForTsnFundingReadiness` can observe that status with an application-supplied fetch function. Retrieve restricted preparation from owner-authenticated `POST /network/funding/readiness` using `{workId, senderPubkey, authorizationSignature}`. `assertTsnFundingReadiness` validates the returned identity, version, commitment, expiry, deposit accounts and amount against the original request. Balance checks are advisory and reserve no wallet funds.

## Approve the funding transaction

Enable an explicit “Approve funding” action only for current matching readiness. The complete [wallet-credit example](https://github.com/bigdreamsweb3/trustlink-pay/blob/main/tsn-protocol/tsn-docs/sdk/examples/credit-deposit.ts) separates initial message approval from later deposit approval. Build the deposit from Node's verified accounts and the original note commitment. The canonical `tcap:funding-root:v1` PDA remains its ninth account. `resolveTcapGpruDepositAccounts` remains a lower-level account reader; it does not replace the readiness decision in the staged flow.

The Node exposes `/network/recent-blockhash` with `recentBlockhash`, `lastValidBlockHeight` and `contextSlot`. Convert those fields into `SenderFundingBlockhashContext`: exactly `{ blockhash, lastValidBlockHeight, contextSlot }`, with a canonical, nonzero 32-byte Base58 hash, a positive safe-integer height and a nonnegative safe-integer slot. Refresh this context after the user chooses funding approval, immediately before transaction signing, and handle the endpoint's HTTP errors. These client-supplied values guide RPC selection and lifetime checks; they do not independently authenticate the issuing RPC or extend the signed hash's lifetime.

The deposit amount follows the current Node contract's authorized payment amount. After wallet signing, `assertSignedTcapGpruWalletDepositTransaction(wire, approvedDeposit, context)` checks the owner signature, accounts, amount, note commitment and exact issued hash without rewriting the signed bytes. The transaction must contain exactly one canonical funded-note deposit. Wallet-added ComputeBudget instructions may set heap size, compute limit, priority price or loaded-account-data limit with valid encoding and no duplicate setting; additional transfers, TCAP actions and Memo instructions remain rejected. Fee policy and any separately supported payment family must be documented from its actual contract.

## Complete the same intent

`buildCompleteTsnFundingRequest` produces the owner-authenticated completion body with the original work ID, expected state version, authorization payload commitment, exact signed wire and issued tuple. Post it to `/network/funding/complete`. Node validates the owner signature and exact deposit; Receiver atomically attaches only those funding fields and creates the deterministic settlement reference. The phase changes to `SIGNED_DEPOSIT`, with a new final payload commitment. Final Node verification reuses the signed private readiness evidence, checks authorization expiry and simulates the unchanged deposit.

Exact completion retries are idempotent; changed wires, stale readiness and conflicting commitments are refused. Retain signed bytes when an outcome is uncertain, reconcile that same work and avoid another wallet approval. Only the final `VERIFIED` deposit becomes eligible for Cranker. Confirmed funding still gates settlement; Node verifies the complete successful deposit receipt and authenticated funded membership before preparing the private transition.

## Confirm and recover

Follow [payment lifecycle and status](/developers/payment-intent-lifecycle), verify funding and settlement separately, and reconcile the private root/epoch transcript and separate aggregate reserve accounting on the selected cluster. An owner also needs validated Memo history and private scan/recovery material to reconstruct the credited balance. Service readiness, accepted work and a single decryptable Memo do not establish all of those conditions.

Confidential debit/exit and arbitrary cross-chain routes are not established end to end by this tutorial. Use the [integration boundary guide](/sdk/integrations) and route-specific evidence before extending a credit integration.
