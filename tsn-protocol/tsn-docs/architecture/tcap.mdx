# TCAP reserve and confidential state

TCAP (Transfer Confidential Asset Protocol) governs approved token assets, their reserve vaults, and protocol liability accounting. It is the asset and accounting layer for TSN's confidential settlement design. TIP supplies identity routing; GPRU is being developed to verify transaction-specific encrypted-state transitions before TCAP changes liabilities.

## Current implementation boundary

The current program source and deployed instruction/account layouts are authoritative for live behavior. Existing credit instructions update opaque TIP-rooted commitment state, but the transition does not itself prove a spendable balance. Confidential debit and exit are fail-closed. The new GPRU program and DNA-based credit/debit flow are not yet deployed.

## Target settlement sequence

```mermaid
sequenceDiagram
    participant Sender
    participant Receiver
    participant Node
    participant Cranker
    participant GPRU
    participant TCAP
    participant Owner as Recipient SDK

    Sender->>Receiver: Signed intent and reserve funding
    Receiver->>Node: Accepted ingress work
    Node->>Node: Resolve TIN via TIP and validate route/asset
    Node->>Node: Derive unique DNA and one-time ElGamal key
    Node->>Cranker: Immutable verified transition
    Cranker->>GPRU: Submit transition and proof
    GPRU->>GPRU: Verify derivation, balance relation, and replay rules
    GPRU->>TCAP: Atomic validated handoff
    TCAP->>TCAP: Update reserve liability
    Owner->>Owner: Recover one-time private key locally; decrypt own state
```

Receiver acceptance is ingress acceptance. Node verification is a separate stage. Cranker submission is not proof of confirmation. TCAP changes reserve accounting only after the future GPRU on-chain verification succeeds atomically.

## Target credit and debit rules

A wallet-to-TIN credit begins with sender-authorized public reserve funding. Node resolves the recipient route and constructs a unique DNA transition; the sender SDK does not resolve recipient TIP state. GPRU verifies that the one-time ElGamal key matches the route scan key and DNA, and that the encrypted successor is valid. TCAP then applies the liability update.

A TIN debit must prove that the prior encrypted balance covers the amount and that the successor is the exact subtraction. A TIN-to-TIN transfer must prove source and destination conservation while hiding the amount and avoiding a shared public transaction identifier. The owner SDK may do a local check for usability, but the program proof is the enforcement boundary.

## Privacy guarantees and limits

The design uses transaction-specific DNA outputs to avoid repeatedly exposing a stable recipient route. Each output has a one-time ElGamal public key that the recipient can recover locally using owner-held secret material. The Node derives the public key but does not receive the private key or plaintext balance.

Public wallet funding and exit still reveal wallet-level metadata. A one-time key commitment binds derivation inputs; it does not prove a valid balance update. GPRU must verify the derivation, encrypted-state proof, asset and policy bindings, sequence, and nullifier before TCAP acts.

## Current status

GPRU exists as a derivation library and integration scaffold. The on-chain GPRU program, encrypted-balance proof verification, and atomic TCAP handoff are not deployed. The deployed TCAP program remains authoritative; confidential debit and exit are disabled.
