The Node verifies Receiver-leased work, resolves private TIN V1 records, constructs TCAP V2 credit transitions, and exposes network status. Receiver owns the durable work queue; Crankers lease work from Receiver, not from Node work endpoints.

## Application and read endpoints

| Method and path | Purpose |
| --- | --- |
| `POST /` | Node health and epoch status. |
| `POST /intents` | Forward payment intent ingress to Receiver; requires Receiver to be configured. |
| `GET /tin-resolution/{tin}` | Resolve a TIN V1 display identity using the Node's protected lookup secret. The TIN itself is a lookup credential; responses are not owner-authenticated, so treat returned identity fields as public to callers who know the TIN. |
| `POST /threshold-access/nonces/consume` | Validate public wallet/device proofs and atomically consume the threshold-access nonce. |
| `GET /metrics` | Node uptime and settlement metrics. |
| `GET /settlement-networks` | Registered destination networks passing route and liquidity checks. |
| `GET /network/overview` | Aggregate network and Cranker status. |
| `GET /epoch/status` | Current epoch state. |

TIN creation is submitted to Receiver `POST /tin-operations` by the SDK. The Node has no public TIN-operation API. Its background worker reads signed work from Receiver and records `VERIFIED` or `REJECTED` decisions through the authenticated internal Receiver contract.

## Internal service endpoints

These endpoints require the configured internal service API key:

| Method and path | Purpose |
| --- | --- |
| `POST /internal/wake` | Payload-free Receiver wake signal for the sleeping Node verifier. |
| `POST /internal/settlement-authorizations/settlement` | Build a short-lived authorization for a Receiver-leased settlement after checking its lease and Node-verified TCAP V2 transition. |

## SDK example

```ts
import { TsnHttpClient } from "@trustlink/tsn-sdk";

const client = new TsnHttpClient({ baseUrl: process.env.TSN_NODE_URL! });
const networks = await client.get("/settlement-networks");
```

Payment intents use the SDK's `buildPaymentAuthorizationIntentRequest` and are submitted to Receiver ingress. The sender supplies the TIN and signed funding transaction, not the recipient route commitments. Node resolves the current TIN V1 TIP route itself. TIN resolution returns display identity only and does not authorize a transfer.

Do not call retired Node `/tin-operations`, `/intent-work`, or direct route-storage endpoints. Receiver is the source of truth for work state and leases.
