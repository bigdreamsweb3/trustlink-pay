This guide describes the application boundary. Your app configures service URLs, displays the recipient and payment details, and asks the connected wallet to approve the exact authorization. TSN services verify the submitted work; a confirmed Solana transaction is the evidence that settlement executed.

The TSN SDK is currently a private workspace package. It is not published to the public npm registry. See the [SDK overview](/sdk/index) for package access and the [SDK reference](/api-reference/sdk/tsn-sdk) for exported functions.

The snippets illustrate integration stages and assume caller-supplied variables. Complete [typed examples](/sdk/payment-guide) and the [full generated reference](/sdk/api-reference) provide verified inputs and signatures.

## Check readiness

Pass the service endpoints selected by your application. A readiness response is not a payment authorization or settlement confirmation.

```ts
import { getTsnNetworkStatus } from "@trustlink/tsn-sdk";

const network = await getTsnNetworkStatus({
  live: {
    node: process.env.TSN_NODE_URL,
    receiver: process.env.TSN_RECEIVER_URL,
    rpc: process.env.TSN_RPC_URL,
  },
});

if (!network.readyForNativeTransactions) {
  throw new Error("TSN services are not ready");
}
```

## Resolve the recipient

TIN resolution returns the owner-provided display identity for the sender to review. In a trusted backend, the SDK can resolve the TIP registry using the protected lookup secret. Never include that secret in browser code or a wallet authorization.

```ts
import { Connection } from "@solana/web3.js";
import { resolveTinV1Identity } from "@trustlink/tsn-sdk/tins";

const recipient = await resolveTinV1Identity({
  connection: new Connection(process.env.TSN_RPC_URL!, "confirmed"),
  tin: recipientTin,
  lookupSecret: process.env.TINS_LOOKUP_SECRET!,
  programId,
});

if (!recipient) throw new Error("TIN could not be resolved");
```

The display name helps the sender confirm the intended recipient; it is not legal identity verification. The wallet should show the amount, asset, recipient TIN, and applicable fee before asking the sender to sign.

## Request wallet authorization

Use the SDK to create a private funding note and build the canonical payment authorization from the reviewed recipient and asset details. Ask the connected wallet to sign that exact message, including its funding-note commitment. Keep the opening in memory and exclude it from logs and persistent browser storage.

```ts
import { Connection, PublicKey } from "@solana/web3.js";
import { createTcapAssetPaymentAuthorization, createFundingNoteV1 } from "@trustlink/tsn-sdk";

const fundingNote = createFundingNoteV1();
const authorization = await createTcapAssetPaymentAuthorization({
  connection: new Connection(process.env.TSN_RPC_URL!, "confirmed"),
  depositor: new PublicKey(senderWallet),
  mint: new PublicKey(tokenMint),
  senderWallet,
  senderIdentity: senderWallet,
  receiverIdentity: `tin:${recipientTin}`,
  recipientDisplayName: recipient.displayName,
  recipientDisplayNameSource: recipient.displayName.trim() ? "owner-provided" : "not provided",
  amount,
  senderFeeAmount,
  totalTokenRequiredUi,
  fundingMode: "tcap_funded_note_v1",
  fundingNoteCommitment: fundingNote.commitment,
});

const signature = await wallet.signMessage(
  new TextEncoder().encode(authorization.message),
);
```

The selected TCAP program must have its canonical global funding root initialized and the updated thirteen-input verifier activated. Responding services alone do not establish those prerequisites; the [payment guide](/sdk/payment-guide) describes the staged application flow.

## Submit the signed intent

Submit the SDK-built request with the sender's message signature and matching private note through the configured protected ingress route. Initial requests reject signed funding bytes and blockhash context. The response identifies accepted work; it does not mean Node verification has completed or that funds have settled.

```ts
import {
  TsnHttpClient,
  buildPaymentAuthorizationIntentRequest,
  type CreateIntentRequest,
  type PublicTsnMempoolIntent,
} from "@trustlink/tsn-sdk";

const request = buildPaymentAuthorizationIntentRequest({
  paymentId,
  recipientHash: recipient.ownerPubkeyHash,
  recipientTin,
  tokenMintAddress: authorization.asset.mint,
  tokenDecimals: authorization.asset.decimals,
  senderWallet,
  senderAuthorizationMessage: authorization.message,
  senderAuthorizationSignature: Buffer.from(signature).toString("base64"),
  senderAuthorizationNonce: authorization.nonce,
  senderAuthorizationIssuedAt: authorization.issuedAt,
  senderAuthorizationExpiresAt: authorization.expiresAt,
  senderFeeAmount,
  senderFundingMode: "tcap_funded_note_v1",
  fundingNote,
  amount,
  source: "my-tsn-app",
});

const client = new TsnHttpClient({ baseUrl: process.env.TSN_NODE_URL! });
const intent = await client.postIntent<CreateIntentRequest, PublicTsnMempoolIntent>(request);
console.log(intent.id, intent.status);
```

## Wait for readiness and approve funding

Retain the same payment ID, message, signature, nonce, amount and private note while Node checks the authorization. Use `waitForTsnFundingReadiness` to observe Receiver's `FUNDING_READY` status, then obtain owner-authenticated preparation from Node's `POST /network/funding/readiness`. `assertTsnFundingReadiness` validates that preparation against the original request before the application enables an explicit funding approval action.

When the sender chooses to approve funding, obtain a fresh blockhash tuple and build `buildTcapGpruWalletDepositTransaction` from the verified deposit accounts, amount and original note commitment. Ask the wallet to sign that exact deposit, then use `buildCompleteTsnFundingRequest` to attach its unchanged bytes and tuple to the same work through `POST /network/funding/complete`. The complete [wallet-credit example](https://github.com/bigdreamsweb3/trustlink-pay/blob/main/tsn-protocol/tsn-docs/sdk/examples/credit-deposit.ts) implements these separate approval steps; all staged helpers are exported from `@trustlink/tsn-sdk`.

Retain the exact signed completion for an uncertain response and retry it without another wallet approval. Follow the [payment lifecycle](/developers/payment-intent-lifecycle) and verify funding and settlement signatures separately on the selected Solana cluster.

For Node, Receiver, Cranker, program-build, and deployment procedures, use the repository's [root documentation](https://github.com/bigdreamsweb3/trustlink-pay/blob/main/docs/laboratory/README.md). This site stays focused on protocol concepts and application SDK use.
