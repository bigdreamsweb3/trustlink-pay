# Replay protection

For a TCAP credit, the Node derives a funding commitment from the signed reserve-deposit transaction. TSN binds that value into the authorization digest and forwards it to TCAP as the transition nullifier. TCAP does not allocate a nullifier PDA or a separate spent-funding account for this flow.

The decisive replay check is TCAP's atomic state transition. Each credit must use the current predecessor commitment and exactly the next sequence. A successful instruction advances both values and records the transition nullifier in the same TIP-rooted state account. Replaying that settlement then presents a stale predecessor and sequence and cannot apply again.

## Credit authorization checks

TCAP also checks the transition's authorization digest, policy, approved asset, GPRU scope, validity window, and nullifier. TSN derives the authorization signer from the digest and invokes TCAP through CPI. GPRU validates the transaction-specific DNA key proof before TSN authorizes the TCAP transition. The Node verifies the signed funding transaction off-chain, and the Mother Node signs the exact settlement message submitted by the Cranker.

The nullifier is a field in the transition ABI, not an account address. In this credit path it carries the funding-derived commitment; TCAP stores only the latest applied nullifier alongside the current commitment and sequence.

## Other replay-protected flows

TSN's epoch settlement and refund paths use their own claim-slot state to make the first valid settlement or refund exclusive. Those accounts are distinct from the TCAP credit replay mechanism and should not be described as a per-credit nullifier registry.

## Safe retry behavior

If submission fails before confirmation, the Cranker may retry the same authorized settlement while the validity window remains open and the predecessor and sequence still match. If a submission confirmed but the response was lost, inspect its signature and current TCAP state; another submission cannot reapply the same transition after the state advances.

When the authorization expires, the Node must check the confirmed funding result and current TCAP state before constructing a replacement authorization. The replacement remains bound to the original funding transaction and current predecessor. This design does not claim a global on-chain spent-funding registry; it uses the funding commitment to bind authorization and TCAP's atomic state transition to reject replay of the same settlement.
